# TM 1.0 产品需求文档

> 版本：v1.0-keep-architecture
> 状态：当前执行基线
> 日期：2026-08-12
> 产品代号：TM 1.0
> 适用项目：`E:\tm数据表格\tmall-dashboard`
> 技术策略：保留 Flask + SQLite + 原生 HTML/CSS/JavaScript

## 1. 文档说明

本文件是当前项目唯一的执行与验收 PRD。功能开发、API 契约、测试范围和发布验收均以本文为准。

根目录 `PRD.md` 保留为历史产品背景和能力参考，不作为当前迭代的范围依据；旧版 `.docx` PRD 已移出仓库。

当前实现采用“不改技术架构”的 TM 1.0 方案。历史方案与当前方案的技术路线差异如下：

| 项目 | TM 1.0 保留原架构版 | TM 2.0 DS 兼容版 |
|---|---|---|
| 前端 | Flask 模板/静态 HTML + 原生 JavaScript + CSS | Vue 3 + TypeScript + Vite |
| 状态管理 | 页面模块状态 + URL 参数 + 轻量公共状态 | Pinia |
| 路由 | Flask 页面路由和前端页面入口 | Vue Router |
| UI 组件 | 项目内原生 CSS/HTML 组件 | DS Commerce 组件和 Naive UI |
| 图表 | ECharts 统一 | ECharts 统一 |
| 后端 | Flask 单体 API | 首期仍可 Flask，未来可接 DS Koa/BFF |
| 数据库 | SQLite | SQLite，未来可迁入 DS 数据服务 |
| 未来接入 DS | 通过 API 或 iframe/外链改造，页面需要适配 | 原生迁入 DS，目标是不重做页面 |

本文档不是在否定原架构。它的价值是：在不迁移前端的前提下，尽快把店铺经营闭环做出来。但必须接受一个事实：**保留原架构可以节省当前前端迁移成本，却不能保证未来进入 DS 时不再做一次前端适配。**

## 2. 产品定位

### 2.1 一句话定位

TM 1.0 是面向单个天猫店铺内部运营团队的经营分析和商品运营闭环工具：统一导入报表，查看店铺经营结果，跟踪净销售目标，分析商品和推广，并记录“目的、动作、结果、复盘”。

### 2.2 当前目标

优先快速可用，解决以下日常问题：

1. 店铺今天和当前周期经营结果如何。
2. 年、季度、月、周、日目标完成到哪里。
3. 哪些商品需要处理，已经创建的动作进行到哪一步。
4. 推广花费是否带来合理产出。
5. 商品处于什么生命周期，是否存在季节经营节点。
6. 报表如何稳定导入，字段和数据质量是否可信。

### 2.3 用户

| 用户 | 主要任务 |
|---|---|
| 店铺负责人 | 首页看数、目标跟踪、查看待办和复盘结果 |
| 商品运营 | 商品诊断、创建运营动作、填写复盘 |
| 推广运营 | 查看渠道、计划、单元和商品推广效率 |
| 数据维护者 | 导入文件、字段映射、质量检查、撤销批次 |

默认是一个店铺和一个内部小团队，不做多店铺和复杂权限体系。

## 3. 范围收敛

### 3.1 固定一级页面

完整产品固定为七个一级页面：

1. 店铺总览
2. 商品经营
3. 推广分析
4. 生命周期
5. 经营复盘
6. 数据中心
7. 设置

### 3.2 保留原架构版的发布范围

| 版本 | 必须可用 | 可以先占位但不得展示假数据 |
|---|---|---|
| 1.0 快速可用 | 数据中心基础导入、店铺总览、目标体系、商品经营、运营动作、动作复盘 | 推广深度下钻、生命周期季节算法、导入撤销 |
| 1.1 分析增强 | 推广分析、生命周期、季节属性、周期复盘、字段/视图模板 | 无 |
| 1.2 稳定维护 | 导入撤销、质量增强、历史版本、性能和可维护性整理 | 无 |

1.0 的上线闭环固定为：

```text
导入 -> 看数 -> 目标 -> 商品动作 -> 结果 -> 复盘
```

未完成 1.0 闭环之前，不新增市场、评价、竞品、关键词、工具箱等一级模块。

### 3.3 明确不做

- 多店铺、多品牌、多公司组织架构。
- 通用 BI 平台、自由拖拽报表、任意公式设计器。
- 复杂预警规则编排平台。
- 通用项目管理、审批流、人员绩效系统。
- AI 自动改价、自动投放、自动执行或自动做经营决策。
- 独立的评价分析、市场分析、竞品分析和关键词机会模块。
- 为未来 DS 复制通用聊天、知识库、任务中心。
- 引入 Vue、React、TypeScript 构建第二套前端。

## 4. 原架构边界

### 4.1 当前架构

```text
Browser
├─ Flask 页面路由
├─ frontend/ 当前工作台页面
├─ templates/ 旧版页面和 partials
├─ static/css 原生样式
└─ static/js / frontend/ui_demo/assets 原生脚本
        |
Flask 单体应用
├─ app.py 页面和应用工厂
├─ api/ Flask API 蓝图
├─ scripts/ 导入和分析脚本
├─ db.py SQLite 连接和迁移
└─ models/ repos/ services/ 逐步整理的业务层
        |
SQLite
├─ 店铺、商品和日/周/月事实
├─ 字段映射和导入批次
├─ 目标、运营动作和复盘
└─ 生命周期、配置和审计
```

### 4.2 什么叫“不改架构”

以下约束必须满足：

- 保留 Flask 作为唯一 Web 服务和 API 服务。
- 保留 SQLite 作为首版唯一数据库。
- 保留原生 HTML/CSS/JavaScript 作为前端运行方式。
- 不引入 Vue Router、Pinia、React、Next.js 或新的前端框架。
- 不引入第二套页面入口和第二套导航体系。
- 不要求把后端迁移到 Koa、Node 或微服务。
- 不改变现有导入脚本的输入方式和主要数据表含义，必要变更通过迁移完成。
- 允许按业务域整理 Flask blueprint、service、repository 和前端 JS 模块，但整理不能改变运行时架构。

### 4.3 允许的渐进整理

保留架构不等于继续维护一个几千行巨型文件。允许以下整理：

- `api/data_api.py` 继续作为兼容入口，但新增能力必须落在独立的业务模块中，再由入口注册。
- 当前 `frontend/` 作为主前端；`templates/` 旧版保留 `/legacy/` 只读访问，不能继续并行开发。
- 把页面脚本按 `overview.js`、`products.js`、`promotion.js`、`lifecycle.js`、`reviews.js`、`data-center.js`、`settings.js` 拆分。
- 把公式、字段字典、格式化、日期和筛选函数放到共享原生 JS/Python 模块。
- 统一使用 ECharts；旧 Chart.js 代码只允许在迁移前兼容，不新增 Chart.js 图表。
- 使用 CSS variables 统一 tokens，但不建立 DS 的 Vue 组件包。

## 5. 全局业务规则

### 5.1 单店铺

- 当前运行实例只有一个当前店铺，不显示店铺切换器。
- 数据表保留 `shop_id`，默认使用一个固定店铺值，为未来扩展预留。
- 不实现组织成员、复杂权限和多租户隔离。

### 5.2 时间与筛选

- 默认显示最新有完整数据的一天。
- 时区固定为 `Asia/Shanghai`。
- 自然周为周一至周日，季度按自然季度。
- 页面共享日期范围、商品、分层、生命周期和推广渠道筛选。
- 页面下钻时继承目标页面支持的筛选；不支持的条件被移除并提示。
- 数据不足时显示“数据截至日期”和缺失范围，不能把缺失当作零。

### 5.3 数据状态

每个数据区域至少区分：加载中、有数据、无数据、数据不足、字段缺失、计算失败、数据源不可用、部分可用。

原生前端使用统一状态渲染函数，不允许每个页面自行创造一套空态和错误提示。

## 6. 指标与数据口径

具体字段清单、来源列映射、R1/R2 状态、类型、粒度、聚合方式、公式依赖和导入模板统一见 [FIELD_DICTIONARY.md](./FIELD_DICTIONARY.md)。1.0 与 2.0 使用同一套标准键；1.0 原生前端可直接使用 snake_case，2.0 由 adapter 转为 DS DTO 的 camelCase。

### 6.1 核心指标

| 指标 | 标准键 | 口径 |
|---|---|---|
| 净销售额 | `net_sales` | 支付金额 - 成功退款金额 |
| 支付金额 | `payment_amount` | 选定周期支付金额汇总 |
| 成功退款金额 | `successful_refund_amount` | 选定周期成功退款金额汇总 |
| 退款率 | `refund_rate` | 成功退款金额 / 支付金额 |
| 商品支付转化率 | `payment_conversion_rate` | 支付买家数 / 商品访客数 |
| 推广花费 | `ad_spend` | 选定周期推广渠道花费汇总 |
| 费比 | `expense_ratio` | 推广花费 / 支付金额 |
| 客单价 | `average_order_value` | 支付金额 / 支付买家数 |
| 老客占比 | `returning_buyer_ratio` | 老客支付买家数 / 支付买家数 |
| 推广 ROI | `ad_roi` | 推广成交金额 / 推广花费 |

除数为零或关键字段缺失时显示“不可计算”和原因，不返回伪造的零值。

### 6.2 统计与归属

- 成功退款金额按退款成功日期归属，不回写原支付日期；某日退款大于支付时，日净销售额允许为负数。
- 店铺日度报表是店铺经营结果首选来源；商品日度数据用于商品分析和对账，不覆盖店铺级事实。
- 推广指标以对应推广报表为来源；退款报表只补充退款事实。
- 同一粒度多来源时，按人工确认的来源模板优先级，再按最新成功批次选择生效记录，并保留冲突信息。
- 店铺与商品汇总差异绝对值大于 1 元或相对值大于 0.1% 时显示对账异常。
- 比率和 ROI 统一采用 `sum_then_derive`：先汇总分子、分母，再计算比率，禁止平均每日或商品比率。
- 店铺级支付买家数和老客支付买家数必须来自可去重的店铺/人群报表，不从商品买家数相加推算。

### 6.3 指标方向

- 净销售额、支付金额、转化率、客单价、老客占比、ROI 上升默认表示改善。
- 退款率、费比上升默认表示恶化。
- 颜色表达必须同时配合文字或图标，不能只依赖颜色。

## 7. 目标体系

### 7.1 维度和原子模型

支持年、季度、月、周、日五个维度。由于自然周可能跨月，不能建成简单的年到日父子树。每日目标是唯一原子值，其他周期按日期集合聚合：

```text
任一周期目标 = 该周期覆盖日期的每日目标之和
```

周按周一至周日聚合；同一天只有一个生效目标值；完成率使用相同日期集合计算。

### 7.2 自动拆解

用户输入年度净销售总目标，或用去年净销售额乘增长倍率生成建议年度目标：

```text
每日建议目标 = 年度目标 × 去年同一自然日净销售额 / 去年全年净销售额
```

- 负净销售额日期历史权重按 0 处理；权重合计为 0 时使用均匀拆解。
- 闰年 2 月 29 日使用去年 2 月 28 日和 3 月 1 日权重均值，再统一归一化。
- 目标最小单位为 0.01 元，舍入差额补到周期最后一个未锁定日期。
- 去年数据不足或没有历史时必须显示“历史数据不足”或“均匀拆解”。

### 7.3 人工调整和锁定

- 可修改年、季、月、周、日任一周期目标并选择锁定。
- 锁定年、季、月、周只锁定该周期合计；只有锁定日才冻结每日数值。
- 修改后只调整未锁定日期，按历史日权重分配剩余额度。
- 年、季、月允许嵌套锁定；日可在任意周期中锁定。
- 为控制原生 JS 版本复杂度，月锁定和跨月周锁定不能同时生效；冲突时阻止保存并展示差额。
- 目标值必须大于等于 0；已结束周期默认冻结，不参与自动重算。
- 同一店铺同一年只有一个生效方案，保存带版本号，版本过期时要求刷新。
- 记录建议值、人工值、调整人、原因、时间和版本。

### 7.4 首页展示

首页同时展示当前日期所属年、季度、月、周、日的目标、实际、完成率和时间进度。目标详情使用页面路由 `/goals/:year`，不做复杂目标设计器。

## 8. 商品运营动作

### 8.1 闭环定义

每条动作只关联一个商品；批量创建生成多条动作并以 `action_group_id` 关联。每条动作必须包含：

1. 目的：问题、目标指标、期望变化、观察窗口。
2. 动作：商品、类型、详情、计划时间、执行人、完成时间。
3. 结果：对比窗口、动作前值、动作后值、变化值、系统回算说明。
4. 复盘：是否有效、原因、经验结论、后续动作、复盘人和时间。

首版动作类型：加价、减价、换主图、换标题、调整 SKU、调整推广、调整库存/上下架、活动报名、其他。

### 8.2 状态机

```text
草稿 -> 待执行 -> 执行中 -> 待观察 -> 待复盘 -> 已完成
          \-> 已阻塞       \-> 计算失败
                    \-> 已取消
```

- 观察窗口结束且数据覆盖最后一天后，在成功导入后或每日检查时回算并转待复盘。
- 数据不足保持待观察并说明缺失日期或字段。
- 阻塞必须填写原因和预计恢复时间；计划结束但未完成增加已逾期标记。
- 回算异常进入计算失败，可修复数据后重算，或手工填写结果和原因。
- 只有填写复盘结论后进入已完成；已完成允许重开并保留历史版本。
- 导入修正或撤销影响观察窗口时，结果标记失效并重算；已完成动作回到待复盘，原结果和复盘保留。

### 8.3 首页待办

首页待办只来自商品运营动作，展示待执行、执行中、待复盘和已逾期动作。排序优先级为：已逾期、待复盘、执行中、待执行；同状态按计划时间升序。不建设通用任务池和自动问题池。

## 9. 生命周期和季节性

### 9.1 生命周期

阶段固定为新品期、成长期、爆发期、成熟期、衰退期、清退期。系统根据上架时长、净销售趋势、流量、转化、推广依赖、峰值和近期衰减给出建议、依据和置信度。

- 生命周期建议至少需要连续 60 天有效数据；不足时仅展示新品期或“数据积累中”。
- 用户可人工调整和锁定；锁定后导入不覆盖，但系统可以提示建议已变化。
- 记录建议值、人工值、调整人、原因、时间和版本。

### 9.2 季节属性

分类固定为常年稳定型、春夏型、秋冬型、单峰季节型、双峰季节型、节日/大促驱动型、暂无明显季节性。

- 季节属性至少需要 12 个完整自然月，建议 24 个月；不足时不输出春夏、秋冬、单双峰结论。
- 少于 12 个月时页面显示“数据积累中”，允许人工维护属性但必须标记人工来源。
- 类目推断只有在导入同口径类目数据时才开放。
- 不能把 618、双十一等单次大促峰值直接当成自然旺季。
- 置信度只有高、中、低三级，不表示统计概率；只有中或高置信度才输出下一关键时间节点。

### 9.3 生命周期页面

展示阶段分布、商品阶段、持续时间、趋势、季节属性、下一节点、置信度、锁定状态、判断依据和阶段迁移记录。1.0 快速可用阶段只展示入口占位，不展示 mock 生命周期结果；1.1 才开放算法结果。

## 10. 页面需求

### 10.1 店铺总览

首页是店铺经营驾驶舱，回答经营结果、目标差额和已有动作进度，不自动把异常转成动作。

页面区域：

1. 数据上下文：数据截至日期、覆盖范围、最近导入时间、质量状态。
2. 经营结果：净销售额、支付金额、退款率、商品支付转化率、费比、客单价、老客占比。
3. 年/季/月/周/日目标完成率。
4. 商品运营动作待办。
5. 净销售额、支付金额、推广花费趋势。
6. 指标为行、日期为列的日度经营矩阵。

日度矩阵默认包含净销售额、支付金额、成功退款金额、退款率、商品访客数、支付买家数、商品支付转化率、推广花费、费比、客单价、老客占比；支持横向滚动、环比提示、缺失标记、来源查看和导出。

### 10.2 商品经营

- 搜索商品标题和 ID。
- 按分层、生命周期、季节属性、销售状态、是否有待办筛选。
- 按净销售额、支付金额、转化率、退款率、费比、ROI 和趋势变化排序。
- 支持固定商品身份列、横向滚动、字段显隐、列顺序和视图模板。
- 1.0 内置基础经营模板；1.1 增加选款、推广效率、退款售后和生命周期模板。
- 支持导出当前筛选结果。
- 快速查看使用侧边抽屉，完整详情使用 `/products/:productId` 独立页面，包含基本信息、指标、趋势、生命周期摘要、历史动作和新建动作入口。

### 10.3 推广分析

- 展示推广花费、推广成交金额、ROI、费比、点击率和转化率。
- 展示花费、成交、ROI 和费比趋势。
- 支持渠道 -> 计划 -> 单元 -> 商品下钻，但只有对应粒度已导入时才开放。
- 展示推广商品的花费、成交、ROI、费比、直接/间接成交和付费占比。
- 点击推广商品跳转商品经营并保留日期和商品条件。

### 10.4 经营复盘

- 默认展示待复盘动作。
- 同屏展示目的、动作、动作前后指标、系统结果和干扰因素。
- 填写是否有效、原因、经验结论和后续动作。
- 支持日/周/月周期复盘；R1 只提供动作复盘，R1.1 提供周期复盘。

### 10.5 数据中心

导入流程：选择报表类型 -> 上传 -> 识别 -> 字段映射 -> 预览 -> 质量校验 -> 确认导入 -> 结果报告。

首版支持店铺日度、商品日/周/月度、推广渠道/计划/单元/商品、退款、新老客报表。每种来源必须有稳定 `source_type`。

字段映射复用 `E:\bi\ecommerce-dashboard` 的字段字典、标准字段、别名和来源模板理念，导入前展示原字段、标准字段、样例值、类型和匹配状态；必填字段未映射时阻止导入。

数据质量检查文件行数、有效行、无效行、日期范围、商品数、重复键、预计新增/更新数量和异常值。导入失败不能留下半完成数据。

建议唯一键：

| 数据域 | 唯一键 |
|---|---|
| 店铺日度 | `shop_id + date` |
| 商品日度 | `shop_id + product_id + date` |
| 商品周度 | `shop_id + product_id + week_start` |
| 商品月度 | `shop_id + product_id + month` |
| 推广渠道日度 | `shop_id + channel + date` |
| 推广计划日度 | `shop_id + channel + campaign_id + date` |
| 推广单元日度 | `shop_id + channel + campaign_id + unit_id + date` |
| 推广商品日度 | `shop_id + channel + product_id + date` |

导入按业务键 upsert；1.2 提供导入批次历史和撤销，撤销只恢复该批次影响的数据并保留审计记录。

### 10.6 设置

- 店铺名称、时区、货币、自然周起始日。
- 年度目标、增长倍率和超额完成阈值。
- 生命周期判断窗口和最低数据量。
- 字段映射模板和商品视图模板。
- 核心指标公式不可任意编辑。

## 11. 原架构数据与代码边界

### 11.1 后端

| 层 | 当前职责 | 约束 |
|---|---|---|
| `app.py` | Flask 应用工厂、页面入口、蓝图注册 | 不继续堆业务计算 |
| `api/` | API 蓝图和参数校验 | 保持旧 endpoint 兼容 |
| `models/` | 业务数据结构和常量 | 新实体按领域增加 |
| `repos/` | SQLite 查询和写入 | 不让页面直接拼 SQL |
| `services/` | 指标、目标、动作、生命周期和导入业务规则 | 公式只保留一个实现 |
| `scripts/` | 报表解析、导入和批处理 | 可被 API 调用但不复制逻辑 |
| `db.py` / `migrations/` | 连接、迁移和事务 | 所有表变更可回放 |

### 11.2 前端

| 模块 | 位置 | 约束 |
|---|---|---|
| 页面入口 | `frontend/` | 作为当前主前端 |
| 旧页面 | `templates/` | 只保留 `/legacy/` 兼容访问，不继续开发 |
| 页面脚本 | `frontend/ui_demo/assets/` 或 `static/js/` | 按页面拆分，禁止继续扩大单体 bundle |
| 样式 | 页面 tokens + 共享 CSS | 统一亮色、暗色、状态色和密度 |
| 图表 | ECharts | 新增图表只使用 ECharts |
| API 调用 | 共享 `api-client.js` | 页面不直接散落 fetch 逻辑 |

### 11.3 原生组件规范

不引入 Vue 组件库，但必须建立原生组件约定：

- 页面 Shell
- 顶部上下文栏
- KPI 卡
- Panel
- Filter Bar
- Date Range Picker
- Data Table
- Status Tag
- Progress
- Drawer/Dialog
- Loading/Empty/Error/Insufficient Data

组件用 CSS class、`data-*` 属性和 JS 工厂函数实现，DOM 结构、状态名和交互语义参照 DS Commerce；未来迁移时替换渲染实现，不改变业务状态。

## 13. API 契约

### 13.1 兼容原则

- 保留旧 endpoint，新增能力按业务域增加稳定接口。
- 页面通过共享 `api-client.js` 调用 API，不在页面中直接拼接接口。
- 响应使用统一 envelope：

```json
{
  "ok": true,
  "data": {},
  "availability": "available",
  "requestId": "..."
}
```

失败响应：

```json
{
  "ok": false,
  "code": "VALIDATION_ERROR",
  "message": "字段映射不完整",
  "details": {},
  "requestId": "..."
}
```

- 无数据使用 `ok: true` 加 `availability: "no-data"`，不使用 500。
- 金额、比例、日期和状态使用固定命名；前端不依赖 SQLite 列名。
- 业务域接口固定为 `overview`、`goals`、`products`、`promotion`、`actions`、`lifecycle`、`reviews`、`imports`、`settings`。

### 13.2 主要接口

| 业务 | 方法 | 接口 |
|---|---|---|
| 总览 | GET | `/api/overview`、`/api/overview/daily-matrix` |
| 目标 | GET/POST/PATCH | `/api/goals`、`/api/goals/:year`、`/api/goals/:year/periods` |
| 商品 | GET/PATCH | `/api/products`、`/api/products/:product_id` |
| 动作 | GET/POST/PATCH | `/api/actions`、`/api/actions/:id`、`/api/actions/:id/review` |
| 推广 | GET | `/api/promotion/summary`、`/api/promotion/trend`、`/api/promotion/drilldown` |
| 生命周期 | GET/PATCH | `/api/lifecycle`、`/api/lifecycle/:product_id` |
| 导入 | POST/GET | `/api/imports/preview`、`/api/imports`、`/api/imports/:id` |
| 设置 | GET/PATCH | `/api/settings`、`/api/field-templates`、`/api/view-templates` |

旧版接口继续兼容，新增页面不得直接依赖旧接口中含义不清的字段。

## 14. 数据模型概念

首版核心实体：Shop、Product、FieldDefinition、MetricDefinition、ImportBatch、FieldMappingTemplate、MetricFact、GoalPlan、GoalPeriod、OperationAction、ActionMeasurement、ActionReview、LifecycleAssessment、SeasonalityAssessment、PeriodReview、AuditLog。

旧库表能承载的实体先复用；缺少字段通过版本化 migration 增加。任何实体都必须有稳定主键、店铺标识、创建/更新时间和必要的审计字段。

## 15. 非功能需求

- 本机或可信内网环境可用，不承诺公网多租户安全。
- 文件上传限制类型、大小和解析资源，文件名不能直接作为磁盘路径。
- 导入失败不得留下半完成数据，目标和动作写入使用事务。
- 商品表采用服务端分页或分批加载，不能一次渲染全部商品历史。
- 日期或筛选变化只请求受影响数据，不整页刷新。
- 1366px 桌面首页已有数据时 5 秒内完成主要区域加载；慢请求显示骨架屏。
- 写操作记录操作者、时间、前值、后值和原因。
- 指标公式、字段别名、金额/比例/日期格式化各自只有一个权威实现。

## 16. 验收标准

### 16.1 1.0 快速可用验收

1. 用户上传支持的报表，看到字段映射、预览、质量检查和导入结果。
2. 导入后首页显示净销售额、支付金额、退款率、商品支付转化率、费比、客单价、老客占比和数据截至日期。
3. 首页显示年、季、月、周、日目标完成率。
4. 用户按去年数据和增长倍率生成年度目标，并完成自动拆解。
5. 用户修改并锁定月份目标后，未锁定每日目标重新分配，总额守恒；月锁定和跨月周锁定冲突时阻止保存。
6. 用户从商品页创建动作，首页展示待办，执行后系统在观察窗口完成结果回算。
7. 用户填写目的、动作、结果、复盘四部分后，动作进入已完成。
8. 重复导入同一文件不产生重复业务事实。

### 16.2 1.1/1.2 验收

- 推广分析按已导入粒度开放下钻，不构造不存在的计划或单元。
- 生命周期在数据不足时展示“数据积累中”，有足够数据时展示阶段、依据、置信度和人工锁定状态。
- 季节属性不足 12 个完整自然月时不输出自然季节结论。
- 1.2 撤销批次只恢复该批次影响的数据，审计记录仍保留。

### 16.3 视觉验收

- 所有已交付页面使用统一 CSS tokens、页面骨架、KPI、Panel、Table、Filter、Drawer 和状态组件。
- 同一指标在首页、商品页、推广页和导出中的名称、格式、颜色语义一致。
- 1366px、1920px、1024px 和 390px 下没有文字遮挡、控件重叠或不可恢复的横向溢出。
- 旧 `/legacy/` 入口不作为主导航，不与新工作台并行展示。

## 17. 未来进入 DS 的现实成本

保留原架构版未来接入 DS 时，以下内容大概率需要适配或重写：

- 原生 HTML 页面改造成 Vue 页面或 Vue 包装组件。
- 页面状态从 URL/全局 JS 状态迁移到 Pinia。
- Flask 页面路由和 DS Vue Router 路由对接。
- 原生 CSS 组件与 DS Commerce 组件的映射和重做。
- 鉴权、店铺上下文、错误处理和 API adapter 接入 Hermes。
- 与 DS contracts 的 DTO、错误码和契约测试对齐。

可以直接复用的资产：

- SQLite 数据和迁移后的表结构。
- 字段字典、字段映射模板、指标公式、去重粒度和导入逻辑。
- 目标拆解算法、运营动作状态和生命周期判断服务。
- ECharts 配置、统一 tokens 和页面信息架构。

因此，保留原架构的优势是当前上线快，代价是未来 DS 接入仍需要一次前端适配；这份方案不承诺“迁入 DS 零改造”。

## 18. 需求变更规则

1. 是否直接服务单店经营结果、目标跟踪、商品动作、生命周期或数据导入？不是则默认不进入 TM。
2. 是否可以放入现有七个一级页面？不能则必须说明新增页面的必要性。
3. 是否复制 DS 的通用能力？是则只保留数据接口和跳转边界，不在 TM 重做。
4. 是否引入新指标、新字段真相源或新组件体系？是则先更新契约和 PRD。
5. 是否影响 1.0 快速可用闭环？影响则进入 1.1 或 1.2，不阻塞首发。

## 19. 与 2.0 方案的选择依据

| 判断项 | 选择保留原架构 | 选择 2.0 DS 兼容架构 |
|---|---|---|
| 当前上线速度 | 更快，可复用现有页面和脚本 | 需要前端迁移 |
| 当前改造量 | 较小，主要是收敛和整理 | 较大，需逐页 Vue 化 |
| 未来 DS 接入 | 需要一次前端适配 | 页面迁移成本低 |
| 视觉统一 | 可通过 CSS 规范做到接近 | 从组件层直接统一 |
| 长期维护 | 原生 JS 模块和状态成本较高 | 与 DS 共享工程模式 |
| 适合场景 | 先快速验证业务闭环 | 明确要长期成为 DS 原生模块 |

本方案适合“马上要用、暂时不迁移前端”的路径；如果 DS 在近期确定承接 TM，2.0 方案的额外前期成本通常低于后续再做一次前端适配的成本。
