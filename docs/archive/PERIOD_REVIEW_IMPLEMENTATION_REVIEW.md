# 周月复盘整改范围审查

审查日期：2026-09-22  
审查范围：`E:\www\tmall-dashboard`、`BOUNDARY_BI_REPLICATION_PLAN.md` 及当前周/月复盘、商品诊断、运营动作实现。  
审查约束：本次只新增本文件，不修改代码。

## 1. 结论摘要

当前实现不是“只做了周复盘、月复盘完全没有能力”。周复盘和月复盘已经共用以下底座：

- 周期解析、环比/同比/自定义对比：`services/period_review_service.py:194-316`
- 经营事实聚合、目标差距、商品 TOP/下滑诊断：`services/period_review_service.py:738-809`、`:851-1009`
- 周/月模板和保存接口：`services/period_review_service.py:54-182`、`api/period_reviews_api.py:136-210`
- 商品动作创建入口：`frontend/ui_demo/assets/period-review-live.js:219-327`
- 动作状态机、观察窗口自动回算、人工验收：`services/actions_service.py:20-28`、`:157-215`

但闭环尚未成立。当前真实状态应判定为：

| 闭环环节 | 当前判断 | 证据与问题 |
| --- | --- | --- |
| 数据事实 | 部分完成 | 周/月都走 `build_context()`，但月度没有独立上下文验收；月复盘实际仍以 `daily_data` 聚合，月度事实来源、覆盖和未完月规则没有冻结。 |
| 原因线索 | 部分完成 | 商品行有访客、转化、客单价、投放、退款和异常标签，但 `system_facts` 只是字符串，未保存公式、来源、覆盖范围；标签也未绑定可审计规则版本。 |
| 创建动作 | 部分完成 | 周/月页面均可创建动作，但统一使用 `purpose_type=increase_sales`、`target_metric=payment_amount`，没有把异常标签、事实快照、原因线索或问题集合结构化带入动作。 |
| 执行跟踪 | 部分完成 | 独立动作中心和状态机可推进、阻塞、观察、回算和复盘；复盘页上下文没有把 `pending_review` 返回给前端，导致页面内验证入口实际断开。 |
| 下期验证 | 未完成 | 没有“上期动作验证”数据块，也没有按相邻周/月将动作结果回流到下一期复盘；完成动作按执行日期只在当前周期短暂出现，下一期不再可见。 |

因此，本项目应按“共享事实与动作底座已存在，周/月决策闭环未完成”继续实施，而不是重做两套周/月页面。

## 2. 关键审查发现

### 2.1 周/月确实共享入口，但月复盘缺少同等强度的证据

`api/period_reviews_api.py:136-210` 对 `day`、`week`、`month` 使用同一个 `/context` 路由；`build_context()` 也按 `period_type` 统一调用事实、商品、市场、动作和异常聚合。月模板在 `services/period_review_service.py:96-182` 中存在，且已有月度保存测试 `tests/test_period_reviews_api.py:20-30`、模板测试 `:42-56`。

但现有强断言主要集中在周上下文：

- `tests/test_period_reviews_api.py:126-180` 验证周事实聚合。
- `tests/test_period_review_product_diagnosis.py:57-210` 的 endpoint 固定为 `/week/2026-W38/context`。
- `tests/test_period_reviews_api.py:291-403` 验证周的环比、自定义对比和下滑排序。

目前没有等价的月度上下文、月度商品诊断、月度动作回流验收。因此“月复盘能调用同一代码”已被证明，“月复盘具有完整闭环能力”尚未被证明。

### 2.2 当前最明确的断点：待复盘动作没有回到复盘上下文

后端 `_actions_block()` 已查询 `pending_review` 并命名为 `review`：`services/period_review_service.py:665-675`。但是 `build_context()` 返回值只暴露：

```text
actions_done
actions_planned
actions_blocked
```

见 `services/period_review_service.py:799-807`，没有 `actions_review`。

前端执行区却明确读取 `context.actions_review`，见 `frontend/ui_demo/assets/period-review-live.js:627-638`，并且已经准备了“提交复盘验收”弹窗和接口调用：`:533-603`。结果是：

1. 动作可以从商品诊断创建。
2. 动作可以在独立动作中心推进到 `pending_review`。
3. 周/月复盘上下文拿不到待复盘动作。
4. 复盘页中的验收入口没有数据可操作。

这是 P0 级闭环断点，周复盘和月复盘都会受影响。

### 2.3 动作来源字段存在，但没有形成“原因线索 -> 动作”的可审计链

页面创建动作时只提交：

- `source_period`
- `source_category_mode`
- 商品 ID
- 自由文本目的、类型和详情

见 `frontend/ui_demo/assets/period-review-live.js:282-299`。后端 `ActionsService.create()` 也只保存这些来源字段，见 `services/actions_service.py:64-88`。

缺失内容包括：

- 来源周期类型（week/month）。
- 来源对比周期和比较口径。
- 触发问题或规则 ID、规则版本。
- 创建时的事实快照及数据质量状态。
- 异常标签对应的原因维度。
- 目标值或预期变化量。

动作虽“能创建”，但无法可靠回答“这个动作是由哪条事实、哪条原因线索触发的”，也无法保证验证时比较的是同一指标口径。这直接违背 `BOUNDARY_BI_REPLICATION_PLAN.md:852-856` 的决策闭环验收要求。

### 2.4 动作查询不是按复盘来源周期闭合，可能串入其他复盘动作

`_actions_block()` 的查询目前主要按执行日期、计划日期和商品品类过滤：

- 已完成动作按 `executed_at` 落在当前周期：`services/period_review_service.py:653-657`。
- 计划动作按 `planned_at >= 当前周期开始日`，没有结束日期上限：`:659-663`。
- 待复盘和阻塞动作按状态查询，没有周期限制：`:665-674`。

这会带来两个问题：

- 周/月复盘可能展示来源于其他周期或其他复盘口径的动作。
- “本期创建的动作”和“本期验证的动作”没有区分，尤其是月复盘会混入跨月观察窗口动作。

动作表虽然有 `source_period` 等字段，但复盘查询没有使用，也没有将其返回到上下文。`product_actions` 表结构见 `db.py:776-823`；复盘表 `period_reviews` 也没有动作关联或问题集合关联，见 `db.py:715-730`。

### 2.5 “下期验证”目前不存在，只存在动作自身的观察窗口回算

动作服务可以按执行日前后各 N 天的 `payment_amount` 计算结果，见 `services/actions_service.py:157-195`；独立动作中心也可以提交人工复盘，见 `frontend/ui_demo/assets/reviews-live.js:54-59`。

这属于“动作中心闭环”，不等于“周/月复盘闭环”：

- 观察结果没有绑定到下一期复盘记录。
- `period_reviews` 没有 action ID、验证状态、验证周期或验证结论字段。
- 完成动作只在 `actions_done` 中按执行日期查询，过了当前执行周期后，下一期复盘看不到它。
- `review_next_action` 留在动作表中，没有汇入下一期的 `actions_planned` 或“上期验证”素材。

因此目前无法在周/月复盘中完整走通：

```text
异常商品 -> 原因线索 -> 创建动作 -> 执行/观察 -> 下期复盘验证 -> 新动作
```

### 2.6 商品诊断已有有效基础，但仍是“事实字段 + 轻量标签”

`tests/test_period_review_product_diagnosis.py:57-101` 已验证商品诊断返回 GSV、净销售、访客、买家、转化、客单价、投放、退款、异常标签和未知项；`tests/test_period_review_product_diagnosis.py:140-172` 也验证缺失值不伪造为 0。这一部分可复用，不应推倒重来。

但当前 `system_facts` 只有 `GSV` 和 `delta` 文本，`anomaly_tags` 由直接比较生成，未携带：

- 规则名称、规则版本和阈值。
- 指标公式、字段来源和数据覆盖。
- 当前周期与对比周期的完整证据。
- “已验证原因”和“待验证假设”的区分。

这属于 P1 级可审计性缺口；在 P0 闭环打通后补齐。

## 3. 按优先级的落地任务

### P0：阻断闭环，必须优先完成

#### P0-1 建立统一的复盘动作关联协议

**目标**：周/月复盘创建的动作可被准确归属、查询和验证。

**实施内容**：

1. 动作来源字段统一为结构化对象，至少包含：
   - `source_period_type`
   - `source_period_key`
   - `source_compare_mode`
   - `source_compare_period_key`
   - `source_category_mode`
   - `source_product_id`
   - `source_problem_key` 或 `source_rule_key`
   - 创建时的诊断事实快照版本/ID
2. 保留现有 `source_period` 兼容字段，但新逻辑不再只依赖一个无类型周期字符串。
3. 复盘上下文返回动作来源字段、动作状态、观察窗口、结果和复盘结论。
4. 查询必须区分：
   - 本期新建/待执行/执行中。
   - 本期已完成。
   - 本期待复盘。
   - 上期动作在本期需要验证的动作。

**依赖**：动作字段协议、周期相邻关系、商品诊断对象定义。

**验收证据**：

- 从 `week/2026-W38` 创建动作后，API 返回完整来源协议。
- 从 `month/2026-08` 创建动作后，API 返回 `source_period_type=month`，不会与周动作混淆。
- 同一商品、不同周期、不同品类创建三条动作，周/月上下文各自只显示符合来源和验证窗口的动作。
- 数据库查询能按 action ID 追溯商品、来源复盘、原因线索和原始快照。

#### P0-2 把待复盘和下期验证回流到周/月复盘上下文

**目标**：修复当前 `actions_review` 未暴露问题，并实现真正的“下期验证”。

**实施内容**：

1. `build_context()` 同时返回 `actions_review`。
2. 增加统一的 `actions_to_verify` 或等价数据块，表示相邻上期已执行、观察窗口已完成或待完成的动作。
3. 周复盘验证上一周动作；月复盘验证上一月动作，并允许展示本月内周动作的月度汇总时明确标注来源周期，不能静默混合。
4. 在复盘页展示观察前值、观察后值、变化、计算状态、失败原因和人工复盘结果。
5. 提交动作验收后，刷新当前复盘和下一期复盘都能看到状态变化；`review_next_action` 进入下一期计划素材或明确的后续动作区。
6. 修正计划动作查询的周期边界，不能只有 `planned_at >= start` 而无 `end` 限制。

**依赖**：P0-1 来源协议；现有动作状态机、`recalculate` 和 `review` 接口可复用。

**验收证据**：

- 创建 W38 动作，推进到 `observing`，补齐窗口后回算为 `pending_review`；GET W38 context 能看到待复盘动作。
- 在 W38 复盘页提交验收后，GET W39 context 能看到“上期动作验证”及结果，不需要手工复制文本。
- 创建 2026-08 月动作，完成后 GET 2026-09 月 context 能看到验证结果；W38/W39 的动作不会无标识地混入月度结果。
- 观察窗口数据不足时显示 `calculation_failed` 或待补数据原因，不能显示为已完成。

#### P0-3 让“原因线索 -> 动作目标 -> 验证指标”保持同一口径

**目标**：动作不再全部默认验证 `payment_amount`，而是能验证实际诊断的原因维度。

**实施内容**：

1. 商品诊断输出结构化 `diagnosis`：原因维度、证据指标、当前值、基线值、变化、未知项。
2. 创建动作时必须选择或继承 `target_metric`，并保存目标方向、目标值/预期变化及数据口径。
3. 对“流量下降、转化下降、客单价下降、投放效率下降、退款率上升”分别定义可验证指标；数据不可用时禁止伪造可验证动作。
4. 动作验收结果回写同一 `target_metric`，并在复盘上下文显示“原因线索是否被验证”。

**依赖**：P0-1；指标注册表和数据可用性状态。

**验收证据**：

- 一个转化下降诊断创建的动作，默认验证转化率而不是支付金额。
- 一个投放效率下降诊断创建的动作，验证 ROI/费比，并显示缺失字段时的不可计算原因。
- 复盘页能同时显示原因证据、动作目标和前后结果，三者的字段口径一致。

#### P0-4 建立周/月对称的闭环验收测试

**目标**：不再只用周接口测试来代表月复盘能力。

**实施内容**：

1. 将周/月上下文测试参数化，至少覆盖事实、对比、商品诊断、动作创建、状态推进、回算、人工验收和下期回流。
2. 增加月度完整链路：`2026-08` 创建动作 -> `2026-09` 验证动作。
3. 增加跨周期、无基线、部分数据、无动作、观察窗口不足、品类不一致场景。
4. 增加浏览器契约：月复盘执行区能看到待复盘和上期验证，不只是月模板按钮存在。

**依赖**：P0-1 至 P0-3 的接口契约先冻结。

**验收证据**：

- 周、月两套参数化测试均通过，且覆盖同一闭环阶段。
- 至少一条真实测试链路证明“创建动作的周期”与“验证动作的下一期”都能从 API 和页面看到。
- `git diff --check`、前端运行时检查和目标测试通过；不以旧的周测试单独作为月度完成证明。

### P1：影响月度可用性、可审计性和结果可信度

#### P1-1 冻结月度事实来源、粒度和完整性规则

当前服务以 `daily_data` 作为周/月共同事实来源，见 `services/period_review_service.py:341-372`、`:738-759`；规划文档又列出了 `monthly_data`。需要明确：

- 月复盘是否以日事实重新汇总，还是优先读取月事实。
- 未完月按有效天、完整月还是截至日比较。
- 月度环比是否严格等长，跨年和退款按哪个日期归属。
- 月度数据缺失时显示 `partial`、`no-data` 还是 `source-unavailable`。

**验收证据**：同一月度输入可由 API 返回 source、grain、coverage、freshness 和缺失字段；周/月页面与导出使用同一口径。

#### P1-2 修正商品下滑集合的边界

当前后端先取当前周期商品集合，再与基线比较，见 `services/period_review_service.py:977-993`。完全没有当前周期记录、但上期有销售的商品可能不会进入下滑榜。应使用当前/基线商品 ID 并集，区分真实 0、无记录和数据缺失。

**验收证据**：商品上期销售、本期无记录时进入“下滑/消失商品”集合；本期缺字段时不被错误判为 0。

#### P1-3 将诊断事实升级为可审计证据对象

把当前字符串型 `system_facts` 和标签升级为结构化证据，至少包含：`field_key`、`value`、`unit`、`formula`、`source`、`source_fields`、`grain`、`coverage`、`availability`、`unknowns`、`rule_version`。

**验收证据**：商品诊断抽屉、API、动作来源和复盘素材引用同一 evidence ID；查看详情可还原计算口径。

#### P1-4 复盘页与动作中心使用同一动作语义

当前复盘页直接显示原始状态值，见 `frontend/ui_demo/assets/period-review-live.js:605-624`，而动作中心有状态中文标签和完整历史，见 `frontend/ui_demo/assets/reviews-live.js:6-7`、`:44-52`。需要统一：状态标签、负责人、计划/执行日期、观察窗口、失败原因、人工结论和历史入口。

**验收证据**：同一 action ID 在周复盘、月复盘、动作中心显示相同状态、版本、结果和历史；状态变更后各页面刷新一致。

### P2：增强能力，不阻断第一条闭环

#### P2-1 规则、问题集合和快照版本化

按规划 `BOUNDARY_BI_REPLICATION_PLAN.md:735-758` 增加 ProblemSet/规则版本/事实快照，使异常商品集合可复现；当前诊断标签先作为过渡，不在 P0 阶段扩张为复杂规则引擎。

#### P2-2 扩展动作可验证指标和批量动作

在 P0 的目标指标协议稳定后，扩展利润、费比、ROI、转化率、退款率、加购率等观察指标，并支持同一问题集合批量创建动作。

#### P2-3 增加复盘导出和链路使用埋点

导出当前周期事实、异常、动作、验证结果和证据；记录商品诊断打开、动作创建、状态推进、验收提交和下期回流使用情况。

#### P2-4 清理实现中的重复定义和兼容层

`services/period_review_service.py` 同时存在旧 `_products_block()`（`:503-555`）和后置覆盖定义（`:851-1009`）。当前运行时以后者为准，但这会增加后续修改误改旧实现的风险。待 P0/P1 稳定后合并为单一定义，并补充模块级契约测试。

## 4. 推荐实施顺序与依赖

采用一条最短可交付路径：

| 顺序 | 工作包 | 依赖 | 交付判定 |
| --- | --- | --- | --- |
| 0 | 冻结闭环对象和字段协议：周期、来源、诊断、动作目标、验证结果 | 无 | 周/月都能使用同一 JSON 契约，字段含义明确 |
| 1 | 后端补齐来源查询、`actions_review`、`actions_to_verify` 和周期边界 | 0 | 周/月 context 能分别返回待执行、待复盘、上期验证 |
| 2 | 前端复盘执行区接入待复盘和下期验证 | 1 | 页面可以推进、回算、验收，并显示结果来源 |
| 3 | 打通原因线索、目标指标和动作验证指标 | 0、1 | 原因、动作、结果三者口径一致 |
| 4 | 周/月对称测试与最小浏览器验收 | 1、2、3 | 周、月各有一条完整闭环证据 |
| 5 | 月度事实口径、结构化证据、下滑并集、语义统一 | 4 | 月度结果可审计、可比较、可复现 |
| 6 | 规则快照、扩展指标、导出、埋点和重复实现清理 | 5 | P2 增强，不影响已完成闭环 |

建议的并行安排：

- 后端任务负责 0、1、3 的接口和查询契约。
- 前端任务在后端契约冻结后负责 2、4 的页面回流和最小场景。
- 复核任务只维护周/月对称验收矩阵，不另起一套月度实现。

## 5. 最小验收证据清单

完成 P0 前，不应以“页面可打开”或“36 个现有测试通过”作为完成依据。至少需要以下证据：

1. `GET /api/period-reviews/week/<key>/context` 和 `GET /api/period-reviews/month/<key>/context` 返回相同闭环结构：事实、诊断、动作队列、待复盘、上期验证、数据状态。
2. 周动作链路：异常商品 -> 诊断事实 -> 创建动作 -> 状态推进 -> 观察窗口回算 -> 待复盘 -> 周期内提交验收 -> 下一周显示验证结果。
3. 月动作链路：异常商品 -> 诊断事实 -> 创建动作 -> 状态推进 -> 观察窗口回算 -> 待复盘 -> 月度提交验收 -> 下一月显示验证结果。
4. 同一 action ID 在数据库、动作 API、周复盘、月复盘和动作中心可追溯，且状态/版本/结果一致。
5. 观察窗口不完整、指标缺失、无对比基线和跨品类时，均保留明确的不可判断原因，不把缺失转成 0 或“已完成”。
6. 月度测试不能只验证保存模板；必须验证月度事实、商品诊断、动作来源、动作回算和下期验证。

## 6. 审查结论

当前最合理的实施决策是：

- 保留现有周/月共用服务和模板结构。
- 先修 P0 的动作回流和周期关联，不先扩展更多 BI 主题。
- 把“动作中心已有状态机”接入复盘上下文，而不是再造一套周/月动作状态。
- 月复盘按同一闭环协议实现，但必须补齐月度事实口径和月到月验证证据。
- 在 P0 验收完成前，不宣称“周月复盘整改完成”；当前只能称为“共享底座已具备，闭环回流待整改”。
