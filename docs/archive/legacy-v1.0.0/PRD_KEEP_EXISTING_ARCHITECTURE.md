# TM 1.0 产品需求文档

> 版本：v1.1-keep-architecture
> 状态：当前执行基线
> 日期：2026-08-13
> 产品代号：TM 1.0
> 适用项目：`E:\tm数据表格\tmall-dashboard`
> 技术策略：保留 Flask + SQLite + 原生 HTML/CSS/JavaScript

## 1. 文档说明

本文件是当前项目唯一的执行与验收 PRD。功能开发、API 契约、测试范围和发布验收均以本文为准。

根目录 `PRD.md` 保留为历史产品背景和能力参考，不作为当前迭代的范围依据；旧版 `.docx` PRD 已移出仓库。

当前实现采用“不改技术架构”的 TM 1.0 方案。历史方案与当前方案的技术路线差异如下：

| 项目 | TM 1.0 保留原架构版 | TM 2.0 DS 兼容版 |
|---|---|---|
| 前端 | Flask 模板/静态 HTML + 原生 JavaScript + CSS | Vue 3 + TypeScript + Vite |
| 状态管理 | 页面模块状态 + URL 参数 + 轻量公共状态 | Pinia |
| 路由 | Flask 页面路由和前端页面入口 | Vue Router |
| UI 组件 | 项目内原生 CSS/HTML 组件 | DS Commerce 组件和 Naive UI |
| 图表 | ECharts 统一 | ECharts 统一 |
| 后端 | Flask 单体 API | 首期仍可 Flask，未来可接 DS Koa/BFF |
| 数据库 | SQLite | SQLite，未来可迁入 DS 数据服务 |
| 未来接入 DS | 通过 API 或 iframe/外链改造，页面需要适配 | 原生迁入 DS，目标是不重做页面 |

本文档不是在否定原架构。它的价值是：在不迁移前端的前提下，尽快把店铺经营闭环做出来。但必须接受一个事实：**保留原架构可以节省当前前端迁移成本，却不能保证未来进入 DS 时不再做一次前端适配。**

## 2. 产品定位

### 2.1 一句话定位

TM 1.0 是面向单个天猫店铺内部运营团队的经营分析和商品运营闭环工具：统一导入报表，查看店铺经营结果，跟踪净销售目标，分析商品和推广，并记录“目的、动作、结果、复盘”。

### 2.2 当前目标

优先快速可用，解决以下日常问题：

1. 店铺今天和当前周期经营结果如何。
2. 年、季度、月、周、日目标完成到哪里。
3. 哪些商品需要处理，已经创建的动作进行到哪一步。
4. 推广花费是否带来合理产出。
5. 商品处于什么生命周期，是否存在季节经营节点。
6. 报表如何稳定导入，字段和数据质量是否可信。

### 2.3 用户

| 用户 | 主要任务 |
|---|---|
| 店铺负责人 | 首页看数、目标跟踪、查看待办和复盘结果 |
| 商品运营 | 商品诊断、创建运营动作、填写复盘 |
| 推广运营 | 查看渠道、计划、单元和商品推广效率 |
| 数据维护者 | 导入文件、字段映射、质量检查、撤销批次 |

默认是一个店铺和一个内部小团队，不做多店铺和复杂权限体系。

## 3. 范围收敛

### 3.1 固定一级页面

完整产品固定为七个一级页面：

1. 店铺总览
2. 商品经营
3. 推广分析
4. 生命周期
5. 经营复盘
6. 数据中心
7. 设置

### 3.2 TM 1.0 GA 发布范围

早期文档使用“1.0 快速可用、1.1 分析增强、1.2 稳定维护”描述开发阶段。当前代码已经提前实现部分原 1.1/1.2 能力，因此这些名称不再作为产品版本号，也不能用于判断当前功能是否属于发布范围。

本文件定义的当前发布目标统一称为 **TM 1.0 GA**。GA 必须同时满足：

| 发布域 | TM 1.0 GA 必须可用 |
|---|---|
| 经营闭环 | 导入、总览、五层目标、商品经营、运营动作、结果回算、动作复盘、周期复盘 |
| 分析能力 | 推广已导入粒度下钻、生命周期与季节性门槛、来源与可用性说明 |
| 数据治理 | 事务导入、幂等业务键、字段映射、质量报告、批次历史、冲突安全撤销、审计 |
| 工作台 | 总览、商品、推广、生命周期、复盘、数据中心、设置七个一级页面 |
| 交付质量 | 全局筛选、统一状态、完整筛选导出、模板真实生效、响应式页面、备份与隔离恢复演练 |

后续 TM 1.1/1.2 仅用于承载新增需求，不得把已经进入 TM 1.0 GA 的能力重新标成“未来功能”。

1.0 的上线闭环固定为：

```text
导入 -> 看数 -> 目标 -> 商品动作 -> 结果 -> 复盘
```

未完成 1.0 闭环之前，不新增市场、评价、竞品、关键词、工具箱等一级模块。

### 3.3 明确不做

- 多店铺、多品牌、多公司组织架构。
- 通用 BI 平台、自由拖拽报表、任意公式设计器。
- 复杂预警规则编排平台。
- 通用项目管理、审批流、人员绩效系统。
- AI 自动改价、自动投放、自动执行或自动做经营决策。
- 独立的评价分析、市场分析、竞品分析和关键词机会模块。
- 为未来 DS 复制通用聊天、知识库、任务中心。
- 引入 Vue、React、TypeScript 构建第二套前端。

## 4. 原架构边界

### 4.1 当前架构

```text
Browser
├─ Flask 页面路由
├─ frontend/ 当前工作台页面
├─ templates/ 旧版页面和 partials
├─ static/css 原生样式
└─ static/js / frontend/ui_demo/assets 原生脚本
        |
Flask 单体应用
├─ app.py 页面和应用工厂
├─ api/ Flask API 蓝图
├─ scripts/ 导入和分析脚本
├─ db.py SQLite 连接和迁移
└─ models/ repos/ services/ 逐步整理的业务层
        |
SQLite
├─ 店铺、商品和日/周/月事实
├─ 字段映射和导入批次
├─ 目标、运营动作和复盘
└─ 生命周期、配置和审计
```

### 4.2 什么叫“不改架构”

以下约束必须满足：

- 保留 Flask 作为唯一 Web 服务和 API 服务。
- 保留 SQLite 作为首版唯一数据库。
- 保留原生 HTML/CSS/JavaScript 作为前端运行方式。
- 不引入 Vue Router、Pinia、React、Next.js 或新的前端框架。
- 不引入第二套页面入口和第二套导航体系。
- 不要求把后端迁移到 Koa、Node 或微服务。
- 不改变现有导入脚本的输入方式和主要数据表含义，必要变更通过迁移完成。
- 允许按业务域整理 Flask blueprint、service、repository 和前端 JS 模块，但整理不能改变运行时架构。

### 4.3 允许的渐进整理

保留架构不等于继续维护一个几千行巨型文件。允许以下整理：

- `api/data_api.py` 继续作为兼容入口，但新增能力必须落在独立的业务模块中，再由入口注册。
- 当前 `frontend/` 作为主前端；`templates/` 旧版保留 `/legacy/` 只读访问，不能继续并行开发。
- 把页面脚本按 `overview.js`、`products.js`、`promotion.js`、`lifecycle.js`、`reviews.js`、`data-center.js`、`settings.js` 拆分。
- 把公式、字段字典、格式化、日期和筛选函数放到共享原生 JS/Python 模块。
- 统一使用 ECharts；旧 Chart.js 代码只允许在迁移前兼容，不新增 Chart.js 图表。
- 使用 CSS variables 统一 tokens，但不建立 DS 的 Vue 组件包。

## 5. 全局业务规则

### 5.1 单店铺

- 当前运行实例只有一个当前店铺，不显示店铺切换器。
- 数据表保留 `shop_id`，默认使用一个固定店铺值，为未来扩展预留。
- 不实现组织成员、复杂权限和多租户隔离。

### 5.2 时间与筛选

- 默认显示最新完整数据日。完整数据日定义为：该日存在当前页面 R1 指标所需的有效事实，导入批次状态为 `completed`，且没有阻断级质量错误。若不存在完整日，使用最新部分可用日并显示 `partial`、数据截至日期和缺失来源；只有数据库完全没有日期时才回退浏览器当天。
- 时区固定为 `Asia/Shanghai`。
- 自然周为周一至周日，季度按自然季度。
- 页面共享日期范围、商品、分层、生命周期和推广渠道筛选。
- 页面下钻时继承目标页面支持的筛选；不支持的条件被移除并提示。
- 数据不足时显示“数据截至日期”和缺失范围，不能把缺失当作零。

共享筛选使用 URL 查询参数作为刷新、前进后退和复制链接后的恢复依据：

| 筛选 | 参数 | 值 |
|---|---|---|
| 开始日期 | `start` | `YYYY-MM-DD` |
| 结束日期 | `end` | `YYYY-MM-DD` |
| 商品 | `product_id` | 稳定商品 ID |
| 分层 | `tier` | 当前店铺已有分层值 |
| 生命周期 | `lifecycle_stage` | 生命周期标准枚举 |
| 推广渠道 | `promotion_channel` | 已导入渠道标准值 |
| 对比方式 | `compare` | `none`、`previous_period`、`year_over_year` |

页面支持矩阵：

| 页面 | 日期 | 商品 | 分层 | 生命周期 | 推广渠道 |
|---|---:|---:|---:|---:|---:|
| 总览 | 是 | 是 | 是 | 是 | 是 |
| 商品 | 是 | 是 | 是 | 是 | 是 |
| 推广 | 是 | 是 | 是 | 否 | 是 |
| 生命周期 | 是 | 是 | 是 | 是 | 否 |
| 复盘 | 是 | 是 | 是 | 是 | 否 |
| 数据中心 | 否 | 否 | 否 | 否 | 否 |
| 设置 | 否 | 否 | 否 | 否 | 否 |

目标详情页只继承日期、商品和分层。任何页面收到不支持的筛选时必须从请求与 URL 中移除，并用一次非阻塞提示列出被移除的筛选，不得静默忽略。

### 5.3 数据状态

API `availability` 只允许以下值：

| 值 | 含义 | 页面要求 |
|---|---|---|
| `available` | 请求成功且数据满足口径 | 正常展示 |
| `no-data` | 条件内没有业务事实 | 空状态，不显示 0 |
| `insufficient-data` | 有事实但数量或时间跨度不足 | 展示现有范围、门槛和缺口 |
| `missing-fields` | 关键字段缺失 | 列出标准字段和受影响指标 |
| `calculation-failed` | 数据存在但计算失败 | 显示 requestId 和重试入口 |
| `source-unavailable` | 所需来源未导入或暂不可访问 | 显示来源名称和接入入口 |
| `partial` | 部分指标或日期可用 | 展示可用部分并标记缺失范围 |

`loading` 是前端请求中的临时状态，不写入 API `availability`。每个数据区域必须覆盖 loading 和上述七种 API 状态；不得把字段缺失、计算失败和来源不可用合并成普通“暂无数据”。

原生前端使用统一状态渲染函数，不允许每个页面自行创造一套空态和错误提示。

## 6. 指标与数据口径

具体字段清单、来源列映射、R1/R2 状态、类型、粒度、聚合方式、公式依赖和导入模板统一见 [FIELD_DICTIONARY.md](./FIELD_DICTIONARY.md)。1.0 与 2.0 使用同一套标准键；1.0 原生前端可直接使用 snake_case，2.0 由 adapter 转为 DS DTO 的 camelCase。

### 6.1 核心指标

| 指标 | 标准键 | 口径 |
|---|---|---|
| 净销售额 | `net_sales` | 支付金额 - 成功退款金额 |
| 支付金额 | `payment_amount` | 选定周期支付金额汇总 |
| 成功退款金额 | `successful_refund_amount` | 选定周期成功退款金额汇总 |
| 退款率 | `refund_rate` | 成功退款金额 / 支付金额 |
| 商品支付转化率 | `payment_conversion_rate` | 支付买家数 / 商品访客数 |
| 推广花费 | `ad_spend` | 选定周期推广渠道花费汇总 |
| 费比 | `expense_ratio` | 推广花费 / 支付金额 |
| 客单价 | `average_order_value` | 支付金额 / 支付买家数 |
| 老客占比 | `returning_buyer_ratio` | 老客支付买家数 / 支付买家数 |
| 推广 ROI | `ad_roi` | 推广成交金额 / 推广花费 |

除数为零或关键字段缺失时显示“不可计算”和原因，不返回伪造的零值。

### 6.2 统计与归属

- 成功退款金额按退款成功日期归属，不回写原支付日期；某日退款大于支付时，日净销售额允许为负数。
- 店铺日度报表是店铺经营结果首选来源；商品日度数据用于商品分析和对账，不覆盖店铺级事实。
- 推广指标以对应推广报表为来源；退款报表只补充退款事实。
- 同一粒度多来源时，按人工确认的来源模板优先级，再按最新成功批次选择生效记录，并保留冲突信息。
- 店铺与商品汇总差异绝对值大于 1 元或相对值大于 0.1% 时显示对账异常。
- 比率和 ROI 统一采用 `sum_then_derive`：先汇总分子、分母，再计算比率，禁止平均每日或商品比率。
- 店铺级支付买家数和老客支付买家数必须来自可去重的店铺/人群报表，不从商品买家数相加推算。

### 6.3 指标方向

- 净销售额、支付金额、转化率、客单价、老客占比、ROI 上升默认表示改善。
- 退款率、费比上升默认表示恶化。
- 颜色表达必须同时配合文字或图标，不能只依赖颜色。

## 7. 目标体系

### 7.1 维度和原子模型

支持年、季度、月、周、日五个维度。由于自然周可能跨月，不能建成简单的年到日父子树。每日目标是唯一原子值，其他周期按日期集合聚合：

```text
任一周期目标 = 该周期覆盖日期的每日目标之和
```

周按周一至周日聚合；同一天只有一个生效目标值；完成率使用相同日期集合计算。

### 7.2 自动拆解

用户输入年度净销售总目标，或用去年净销售额乘增长倍率生成建议年度目标：

```text
每日建议目标 = 年度目标 × 去年同一自然日净销售额 / 去年全年净销售额
```

- 负净销售额日期历史权重按 0 处理；权重合计为 0 时使用均匀拆解。
- 闰年 2 月 29 日使用去年 2 月 28 日和 3 月 1 日权重均值，再统一归一化。
- 目标最小单位为 0.01 元，舍入差额补到周期最后一个未锁定日期。
- 去年数据不足或没有历史时必须显示“历史数据不足”或“均匀拆解”。

### 7.3 人工调整和锁定

- 可修改年、季、月、周、日任一周期目标并选择锁定。
- 锁定年、季、月、周只锁定该周期合计；只有锁定日才冻结每日数值。
- 修改后只调整未锁定日期，按历史日权重分配剩余额度。
- 年、季、月允许嵌套锁定；日可在任意周期中锁定。
- 为控制原生 JS 版本复杂度，月锁定和跨月周锁定不能同时生效；冲突时阻止保存并展示差额。
- 目标值必须大于等于 0；已结束周期默认冻结，不参与自动重算。
- 同一店铺同一年只有一个生效方案，保存带版本号，版本过期时要求刷新。
- 记录建议值、人工值、调整人、原因、时间和版本。

### 7.4 首页展示

首页同时展示当前日期所属年、季度、月、周、日的目标、实际、完成率和时间进度。目标详情使用页面路由 `/goals/:year`，不做复杂目标设计器。

## 8. 商品运营动作

### 8.1 闭环定义

每条动作只关联一个商品；批量创建生成多条动作并以 `action_group_id` 关联。每条动作必须包含：

1. 目的：问题、目标指标、期望变化、观察窗口。
2. 动作：商品、类型、详情、计划时间、执行人、完成时间。
3. 结果：对比窗口、动作前值、动作后值、变化值、系统回算说明。
4. 复盘：是否有效、原因、经验结论、后续动作、复盘人和时间。

首版动作类型：加价、减价、换主图、换标题、调整 SKU、调整推广、调整库存/上下架、活动报名、其他。

### 8.2 状态机

```text
草稿 -> 待执行 -> 执行中 -> 待观察 -> 待复盘 -> 已完成
          \-> 已阻塞       \-> 计算失败
                    \-> 已取消
```

- 观察窗口结束且数据覆盖最后一天后，在成功导入后或每日检查时回算并转待复盘。
- 数据不足保持待观察并说明缺失日期或字段。
- 阻塞必须填写原因和预计恢复时间；计划结束但未完成增加已逾期标记。
- 回算异常进入计算失败，可修复数据后重算，或手工填写结果和原因。
- 只有填写复盘结论后进入已完成；已完成允许重开并保留历史版本。
- 导入修正或撤销影响观察窗口时，结果标记失效并重算；已完成动作回到待复盘，原结果和复盘保留。

### 8.3 首页待办

首页待办只来自商品运营动作，展示待执行、执行中、待复盘和已逾期动作。排序优先级为：已逾期、待复盘、执行中、待执行；同状态按计划时间升序。不建设通用任务池和自动问题池。

## 9. 生命周期和季节性

### 9.1 生命周期

阶段固定为新品期、成长期、爆发期、成熟期、衰退期、清退期。系统根据上架时长、净销售趋势、流量、转化、推广依赖、峰值和近期衰减给出建议、依据和置信度。

- 生命周期建议至少需要连续 60 天有效数据；不足时仅展示新品期或“数据积累中”。
- 用户可人工调整和锁定；锁定后导入不覆盖，但系统可以提示建议已变化。
- 记录建议值、人工值、调整人、原因、时间和版本。

### 9.2 季节属性

分类固定为常年稳定型、春夏型、秋冬型、单峰季节型、双峰季节型、节日/大促驱动型、暂无明显季节性。

- 季节属性至少需要 12 个完整自然月，建议 24 个月；不足时不输出春夏、秋冬、单双峰结论。
- 少于 12 个月时页面显示“数据积累中”，允许人工维护属性但必须标记人工来源。
- 类目推断只有在导入同口径类目数据时才开放。
- 不能把 618、双十一等单次大促峰值直接当成自然旺季。
- 置信度只有高、中、低三级，不表示统计概率；只有中或高置信度才输出下一关键时间节点。

### 9.3 生命周期页面

展示阶段分布、商品阶段、持续时间、趋势、季节属性、下一节点、置信度、锁定状态、判断依据和阶段迁移记录。TM 1.0 GA 开放算法结果，但必须遵守 60 个连续有效日和 12 个完整自然月门槛；不足时只展示可用性说明，不展示 mock 结论。

## 10. 页面需求

### 10.1 店铺总览

首页是店铺经营驾驶舱，回答经营结果、目标差额和已有动作进度，不自动把异常转成动作。

页面区域：

1. 数据上下文：数据截至日期、覆盖范围、最近导入时间、质量状态。
2. 经营结果：净销售额、支付金额、退款率、商品支付转化率、费比、客单价、老客占比。
3. 年/季/月/周/日目标完成率。
4. 商品运营动作待办。
5. 净销售额、支付金额、推广花费趋势。
6. 指标为行、日期为列的日度经营矩阵。

日度矩阵默认包含净销售额、支付金额、成功退款金额、退款率、商品访客数、支付买家数、商品支付转化率、推广花费、费比、客单价、老客占比；支持横向滚动、环比提示、缺失标记、来源查看和导出。

- 老客占比只使用店铺级可去重事实，公式为 `sum(returning_payment_buyers) / sum(payment_buyers)`；商品级买家不得相加替代。
- 每日环比以所选日期范围内前一个有数据自然日为基准；没有基准日时显示“无可比日期”，不得显示 0%。
- 缺失标记必须返回具体缺失日期或连续日期范围，并指出缺失字段或来源。
- 来源查看至少显示 `source_batch_id`、来源类型、文件名、完成时间和质量摘要，可跳转到数据中心对应批次。
- 矩阵导出使用相同筛选和口径导出全部结果，不以当前 DOM、可见列或首屏日期为边界。

### 10.2 商品经营

- 搜索商品标题和 ID。
- 按分层、生命周期、季节属性、销售状态、是否有待办筛选。
- 按净销售额、支付金额、转化率、退款率、费比、ROI 和趋势变化排序。
- 支持固定商品身份列、横向滚动、字段显隐、列顺序和视图模板。
- TM 1.0 GA 内置基础经营、选款、推广效率、退款售后和生命周期五个模板。模板只控制字段集合与列顺序，不改变指标公式。
- 支持导出当前筛选结果。
- 商品列表“详情”直接打开共享完整详情弹窗，一次展示基本信息、经营/推广指标、日趋势、生命周期、备注、标签、历史动作和新建动作入口，不再先开轻量抽屉后进行第二次下钻。
- `/products/:productId` 仅保留为兼容历史深链接，不作为正常操作入口。

### 10.3 推广分析

- 展示推广花费、推广成交金额、ROI、费比、点击率和转化率。
- 展示花费、成交、ROI 和费比趋势。
- 支持渠道 -> 计划 -> 单元 -> 商品下钻，但只有对应粒度已导入时才开放。
- 展示推广商品的花费、成交、ROI、费比、直接/间接成交和付费占比。
- 点击推广商品、商品粒度结果或推广预警，均在当前页打开与商品经营页相同的完整商品详情弹窗，并传入当前推广指标作为上下文。
- 推广预警读取持久化的 `promotion_product` 规则；同一商品同一指标命中多条规则时只显示最高级别结果。

### 10.4 经营复盘

- 默认展示待复盘动作。
- 同屏展示目的、动作、动作前后指标、系统结果和干扰因素。
- 填写是否有效、原因、经验结论和后续动作。
- TM 1.0 GA 支持动作复盘和日/周/月周期复盘。

### 10.5 数据中心

数据中心不是单一的“上传文件”入口，而是统一承载三种数据接入方式。三种方式最终都必须进入同一套字段映射、质量门禁、批次审计和幂等入库协议。

#### 10.5.1 手动导表（当前 GA）

用户选择报表类型和一个或多个 `.xlsx`、`.xls`、`.csv` 或 `.zip` 文件，系统依次执行：上传 -> 识别 -> 字段映射 -> 预览 -> 质量校验 -> 人工确认 -> 事务入库 -> 结果报告。

手动导表支持多选和全选。预览阶段不得写入正式事实表；必填字段、有效行数、重复业务键或数据质量不满足要求时，确认按钮必须保持阻断。

#### 10.5.2 固定目录定时扫描（下一阶段）

用户配置受控的源目录（`imports_root`）、文件规则（`file_pattern`）和扫描计划（`cron`）。调度器按规则发现新文件，提取文件日期和报表类型，只处理尚未成功入库且日期最新的候选文件，并生成待确认批次。

固定目录扫描不得绕过手动导表的预览和质量门禁。每次扫描必须记录扫描时间、目录、匹配规则、候选文件、跳过原因、文件 SHA-256 和最新业务日期；同一文件或同一业务键重复发现时必须幂等处理。目录不可读、日期无法解析、文件规则不匹配或最新日期缺失时，任务进入可审计的失败/待处理状态，不得静默写入。

#### 10.5.3 AI 扫描/采集处理（未来阶段）

AI 能力用于识别来源、发现文件或页面数据、推断报表类型、辅助字段映射和提出采集处理建议。AI 输出只能生成候选文件、候选映射和待确认批次，不能直接把未经验证的结果写入正式经营事实。

AI 采集必须保留来源地址或文件、采集时间、原始响应/文件指纹、处理提示版本、字段映射结果、质量异常和人工确认记录；采集失败、来源变化或模型置信度不足时，必须转人工处理。AI 方式与手动导表、固定目录扫描共用同一入库 API，不另造一套事实表。

三种方式的交付优先级为：手动导表 -> 固定目录定时扫描 -> AI 扫描/采集。当前版本只承诺第一种；第二种进入下一阶段设计，第三种保留为未来扩展边界。

手动导表的标准流程为：选择报表类型 -> 上传 -> 识别 -> 字段映射 -> 预览 -> 质量校验 -> 确认导入 -> 结果报告。

手动导表首版支持店铺日度、商品日/周/月度、推广渠道/计划/单元/商品、退款、新老客报表。每种来源必须有稳定 `source_type`；固定目录和 AI 方式也必须复用同一 `source_type` 体系。

字段映射以本仓库 [FIELD_DICTIONARY.md](./FIELD_DICTIONARY.md) 为唯一权威来源。导入前展示原字段、标准字段、样例值、推断类型和匹配状态；必填字段未映射时阻止导入。

推断类型只允许 `date`、`integer`、`decimal`、`text`、`empty`。匹配状态只允许：

| 状态 | 含义 |
|---|---|
| `exact` | 源列名等于标准键 |
| `alias` | 命中字段字典别名 |
| `template` | 命中当前来源保存的映射模板 |
| `manual` | 用户在本次预览中手工选择 |
| `unmatched` | 未识别 |

匹配优先级为 `manual > template > exact > alias > unmatched`。保存模板仅对相同 `source_type` 生效；模板引用的源列不存在时保留自动识别结果，并列出未应用项。

数据质量检查文件行数、有效行、无效行、日期范围、商品数、重复键、预计新增/更新数量和异常值。异常明细至少保留前 25 条，包含 Excel 行号、标准字段、原值和原因。导入失败不能留下半完成数据。

最终结果报告至少包含批次 ID、`source_type`、文件名、SHA-256 摘要、日期范围、新增/更新/跳过/无效行数、质量结论、完成时间和审计入口。

建议唯一键：

| 数据域 | 唯一键 |
|---|---|
| 店铺日度 | `shop_id + date` |
| 商品日度 | `shop_id + product_id + date` |
| 商品周度 | `shop_id + product_id + week_start` |
| 商品月度 | `shop_id + product_id + month` |
| 推广渠道日度 | `shop_id + channel + date` |
| 推广计划日度 | `shop_id + channel + campaign_id + date` |
| 推广单元日度 | `shop_id + channel + campaign_id + unit_id + date` |
| 推广商品日度 | `shop_id + channel + product_id + date` |

**当前运行边界**：店铺日度事实、商品日度事实、推广日度事实、来源观测和导入批次已按 `shop_id` 隔离；`weekly_data`、`monthly_data`、`paid_detail`、商品生命周期/动作及店铺目标仍沿用原有单店表结构。非 `default` 店铺对这些旧表依赖接口以及周/月导入采用 `UNSUPPORTED_SCOPE` fail-closed，不返回跨店数据；导入列表、批次审计和撤销只允许访问当前店铺批次。多店上线前必须为这些表补齐店铺键、迁移唯一约束，并为生命周期、动作、目标和导出补充店铺过滤，不能仅依赖请求参数。

导入按业务键 upsert；TM 1.0 GA 提供导入批次历史和撤销，撤销只恢复该批次影响且未被后续批次覆盖的数据，并保留审计记录。存在后续覆盖时返回 409，不做部分静默撤销。

### 10.6 设置

- 店铺名称、时区、货币、自然周起始日。
- 年度目标、增长倍率和超额完成阈值。
- 生命周期判断窗口和最低数据量。
- 字段映射模板、商品视图模板和推广字段模板。
- 店铺与推广商品预警规则（名称、作用域、指标、运算符、阈值、级别、启用状态）。
- 核心指标公式不可任意编辑。

设置页面必须提供结构化模板管理，不要求用户直接编辑 JSON：

- 映射模板结构为 `{source_type: {standard_key: source_column}}`。
- 商品视图模板结构为 `{template_key: {label, columns}}`。
- 推广字段模板结构为 `{products|keywords|crowd|site: {template_key: {label, columns}}}`。
- `columns` 只能引用商品页字段白名单，顺序即展示顺序，至少保留一个字段。
- 内置模板不可删除；用户模板可新增、重命名、删除和设为默认。
- 保存后的映射模板必须被数据中心读取并应用，商品与推广视图模板必须由 `/api/settings` 持久化并在刷新、换页和重新打开浏览器后恢复；本地存储只保存当前选择偏好，不能保存模板定义。
- 设置页管理全部预警规则，推广页提供推广商品规则快捷入口；保存后 `/api/promotion` 的 `alerts` 必须立即按新规则变化。

## 13. API 契约

### 13.1 兼容原则

- 保留旧 endpoint，新增能力按业务域增加稳定接口。
- 页面通过共享 `frontend/ui_demo/assets/api.js` 调用 API，不在页面中直接散落 `fetch` 和 envelope 解析逻辑。
- 响应使用统一 envelope：

```json
{
  "ok": true,
  "data": {},
  "availability": "available",
  "requestId": "..."
}
```

失败响应：

```json
{
  "ok": false,
  "code": "VALIDATION_ERROR",
  "message": "字段映射不完整",
  "details": {},
  "requestId": "..."
}
```

- 无数据使用 `ok: true` 加 `availability: "no-data"`，不使用 500。
- 金额、比例、日期和状态使用固定命名；前端不依赖 SQLite 列名。
- 业务域接口固定为 `overview`、`goals`、`products`、`promotion`、`actions`、`lifecycle`、`reviews`、`imports`、`settings`。

标准成功响应中 `availability` 必须使用第 5.3 节枚举；`requestId` 必须为非空字符串。部分可用响应在 `details` 中返回缺失范围、字段或来源，页面不得解析错误文案来判断状态。

导出定义：

- “导出当前筛选结果”是以当前共享筛选、页面筛选、排序和字段模板为输入，由服务端分页读取全部匹配记录后生成结果。
- 导出不等同于复制当前 DOM 表格，不受当前页码、虚拟滚动、折叠区域或当前可见行限制。
- 导出字段顺序遵循当前视图模板；金额、比例、日期使用与页面相同的标准键和格式。
- 数据量超过同步导出阈值时可转异步任务，但任务必须保留筛选快照、状态、失败原因、完成时间和下载入口。

### 13.2 主要接口

| 业务 | 方法 | 接口 |
|---|---|---|
| 总览 | GET | `/api/overview`、`/api/overview/daily-matrix` |
| 目标 | GET/POST/PATCH | `/api/goals`、`/api/goals/:year`、`/api/goals/:year/periods` |
| 商品 | GET/PATCH | `/api/products`、`/api/products/:product_id` |
| 动作 | GET/POST/PATCH | `/api/actions`、`/api/actions/:id`、`/api/actions/:id/review` |
| 推广 | GET | `/api/promotion`，使用 `grain` 和筛选参数完成已导入粒度下钻 |
| 生命周期 | GET/PUT | `/api/lifecycle/assessments`、`/api/lifecycle/:product_id`、`/api/lifecycle/:product_id/history` |
| 导入 | POST/GET | `/api/imports/preview`、`/api/imports`、`/api/imports/:id/revert` |
| 设置 | GET/PUT | `/api/settings`；字段映射与商品视图模板作为设置 DTO 的结构化字段 |

旧版接口继续兼容，新增页面不得直接依赖旧接口中含义不清的字段。

关键 DTO 补充：

```json
{
  "filters": {
    "start": "2026-08-01",
    "end": "2026-08-13",
    "product_id": null,
    "tier": null,
    "lifecycle_stage": null,
    "promotion_channel": null,
    "compare": "previous_period"
  },
  "missing_ranges": [{"start": "2026-08-05", "end": "2026-08-06", "reason": "missing-fields"}],
  "source_batches": [{"id": "batch-id", "source_type": "store_day", "source_filename": "store.xlsx", "completed_at": "2026-08-13T09:00:00+08:00"}]

```

字段可为 `null`，但不得缺少已声明键后让前端猜测含义。日期使用 `YYYY-MM-DD`，时间使用带时区 ISO 8601。

## 14. 数据模型概念

首版核心实体：Shop、Product、FieldDefinition、MetricDefinition、ImportBatch、FieldMappingTemplate、MetricFact、GoalPlan、GoalPeriod、OperationAction、ActionMeasurement、ActionReview、LifecycleAssessment、SeasonalityAssessment、PeriodReview、AuditLog。

旧库表能承载的实体先复用；缺少字段通过版本化 migration 增加。任何实体都必须有稳定主键、店铺标识、创建/更新时间和必要的审计字段。

## 15. 非功能需求

- 本机或可信内网环境可用，不承诺公网多租户安全。
- 文件上传限制类型、大小和解析资源，文件名不能直接作为磁盘路径。
- 导入失败不得留下半完成数据，目标和动作写入使用事务。
- 商品表采用服务端分页或分批加载，不能一次渲染全部商品历史。
- 日期或筛选变化只请求受影响数据，不整页刷新。
- 1366px 桌面首页已有数据时 5 秒内完成主要区域加载；慢请求显示骨架屏。
- 写操作记录操作者、时间、前值、后值和原因。
- 指标公式、字段别名、金额/比例/日期格式化各自只有一个权威实现。

## 17. 未来进入 DS 的现实成本

保留原架构版未来接入 DS 时，以下内容大概率需要适配或重写：

- 原生 HTML 页面改造成 Vue 页面或 Vue 包装组件。
- 页面状态从 URL/全局 JS 状态迁移到 Pinia。
- Flask 页面路由和 DS Vue Router 路由对接。
- 原生 CSS 组件与 DS Commerce 组件的映射和重做。
- 鉴权、店铺上下文、错误处理和 API adapter 接入 Hermes。
- 与 DS contracts 的 DTO、错误码和契约测试对齐。

可以直接复用的资产：

- SQLite 数据和迁移后的表结构。
- 字段字典、字段映射模板、指标公式、去重粒度和导入逻辑。
- 目标拆解算法、运营动作状态和生命周期判断服务。
- ECharts 配置、统一 tokens 和页面信息架构。

因此，保留原架构的优势是当前上线快，代价是未来 DS 接入仍需要一次前端适配；这份方案不承诺“迁入 DS 零改造”。

## 18. 需求变更规则

1. 是否直接服务单店经营结果、目标跟踪、商品动作、生命周期或数据导入？不是则默认不进入 TM。
2. 是否可以放入现有七个一级页面？不能则必须说明新增页面的必要性。
3. 是否复制 DS 的通用能力？是则只保留数据接口和跳转边界，不在 TM 重做。
4. 是否引入新指标、新字段真相源或新组件体系？是则先更新契约和 PRD。
5. 是否影响 TM 1.0 GA 的经营闭环、数据正确性或发布门禁？影响则进入当前 GA 收口；不影响才进入后续版本候选。

## 19. 与 2.0 方案的选择依据

| 判断项 | 选择保留原架构 | 选择 2.0 DS 兼容架构 |
|---|---|---|
| 当前上线速度 | 更快，可复用现有页面和脚本 | 需要前端迁移 |
| 当前改造量 | 较小，主要是收敛和整理 | 较大，需逐页 Vue 化 |
| 未来 DS 接入 | 需要一次前端适配 | 页面迁移成本低 |
| 视觉统一 | 可通过 CSS 规范做到接近 | 从组件层直接统一 |
| 长期维护 | 原生 JS 模块和状态成本较高 | 与 DS 共享工程模式 |
| 适合场景 | 先快速验证业务闭环 | 明确要长期成为 DS 原生模块 |

本方案适合“马上要用、暂时不迁移前端”的路径；如果 DS 在近期确定承接 TM，2.0 方案的额外前期成本通常低于后续再做一次前端适配的成本。
## 20. 2026-08-14 PRD 增补：数据、能力、页面与证据体系

本节吸收 `E:\DS_AI_AGENT` 和 `E:\bi\ecommerce-dashboard` 中可复用的治理与 BI 建模经验，作为 TM 1.0 的执行约束。只吸收数据合同、状态模型、证据链和验收方法，不引入 Next.js、React、Radix、Vue 或其他新前端技术栈。

### 20.1 数据健康与能力合同

所有数据域和业务能力 API 必须返回结构化状态，至少包括：`availability`、`evidence_level`、`domains`、`capabilities`、`missing_inputs`、`limitations`、`filters`、`source_batches`、`freshness`、`evidence`、`assumptions` 和 `unknowns`。

数据域健康至少包含来源表、行数、起止日期、`ready/partial/missing` 状态、当前导入批次和补数入口。数据域存在不等于业务能力可用：广告表存在不代表支持商品广告归因，订单金额存在不代表支持利润计算，商品表存在不代表支持流量漏斗。

缺少依赖字段或日期覆盖不足时，页面必须显示 `missing_inputs` 和 `limitations`，不得用默认 0、空排名或模拟结论代替。

### 20.2 字段字典与公式注册表

新增或修改指标前，必须先更新字段字典和公式注册表。注册信息至少包含：`key`、显示名称、描述、单位、原始/派生标识、来源数据域、`depends_on`、`expression`、聚合方式、空值策略、可用页面和限制说明。

比例和 ROI 必须先汇总分子、分母再计算；依赖字段缺失或分母为零时返回明确不可计算状态。页面不得自行实现同一指标的第二套公式。

### 20.3 页面、能力与弹窗注册表

页面能力注册表是页面语义唯一来源，包含 `PageDefinition`、`CapabilityDefinition` 和 `SurfaceDefinition`。每条定义必须声明数据依赖、支持级别（`supported/conditional/unsupported/unclassified`）、数据可用性、交互状态（`enabled/disabled/hidden`）、正式 API、跳转参数、owner、目标文件和验收 selector。

弹窗统一分为：`detail`（只读证据）、`edit`（实体修改）、`config`（口径/模板/规则配置）、`flow`（导入/撤销/状态迁移/锁定/复盘等有副作用流程）。动态创建的 dialog/drawer 也必须带注册 key 和 `data-modal-kind`。

### 20.4 经营闭环

经营页面统一遵循：`观察事实 → 定位对象 → 解释原因 → 创建动作 → 执行动作 → 观察窗口 → 回算结果 → 复盘沉淀`。每个动作必须追溯来源页面、筛选条件、指标快照、目标对象、观察窗口、执行前后值、证据、未知项、操作人和复盘结论。证据不足时可以创建“待补证据”任务，但不得生成确定性经营结论。

### 20.5 页面验收与发布门禁

页面交付必须同时满足：注册表、API 和渲染结果一致；required selector 存在；不存在 `TODO`、`placeholder`、`demo only`；无未处理 console error 和 request failure；`available`、`partial`、`no-data`、`missing-fields`、`insufficient-data` 状态均能稳定渲染；弹窗关闭后焦点恢复；跨页面跳转保留筛选条件。

验收报告必须区分：

```text
implemented       已有代码
preview_verified  本地预览验证通过
data_ready        真实数据满足能力前置条件
production_ready  正式环境证据和运行门禁通过
```

本地预览、API 200 或页面存在都不能单独作为正式发布证据。

### 20.6 本阶段不引入

- 不迁移到 Next.js、React、Vue 或新的 UI 组件库。
- 不因为参考项目存在库存、成本、利润、用户 cohort 等页面，就在当前数据不足时新增承诺。
- 不把 AI 助手、技能工作台或复杂生产发布平台列入 TM 1.0 GA。
- 不把参考项目自身的 blocked 状态或本地预览结果当作 TM 的生产证据。

### 20.7 增补验收标准

1. 数据能力 API 能返回数据域健康、业务能力、缺失输入、限制和来源批次。
2. 字段字典和公式注册表能追溯到页面使用处。
3. 正式页面、上下文页面和弹窗均有注册项，`unclassified` 为零。
4. Data Center 能按数据域、页面、能力和弹窗查看状态及限制。
5. 缺少依赖字段时，不显示伪造的 0、排名、机会或经营结论。
6. 页面验收报告能区分代码存在、本地验证、数据就绪和正式发布四种状态。

### 20.8 写入接口证据合同

所有会改变导入、目标、规则、动作、生命周期、设置或复盘状态的接口，成功响应除 `data` 外必须返回可审计上下文：

| 写入类型 | 必须返回的证据 | 成功状态要求 |
|---|---|---|
| 导入预览 | `preview_id`、来源文件、来源类型、行数、有效/无效行、缺失字段、日期范围 | 缺少必填映射返回 `missing-fields`；存在质量异常返回 `partial`；不得显示为 `available` |
| 导入确认 | `batch_id`、来源文件、日期范围、插入/更新数量、质量结论、完成时间、审计入口 | 批次可由 `source_batches` 和 `evidence` 定位；重复导入仍保持幂等 |
| 批次撤销 | 批次 ID、恢复数量、跳过数量、影响范围和冲突说明 | 有跳过记录时返回 `unknowns`，不得宣称完全恢复 |
| 目标创建/调整/锁定 | 年份、版本、周期、目标值、操作者、原因，以及 `goal_versions`、`daily_goals`、`goal_adjustments` 或 `goal_locks` 证据 | 版本冲突返回 `CONFLICT`，成功写入必须保留审计记录 |
| 预警规则创建/修改/删除 | 规则 ID、规则表动作、操作者和原因 | 规则变更后推广页面立即使用新规则；删除也必须留审计记录 |
| 商品动作创建/批量创建/状态迁移/回算/复盘 | 动作 ID 或动作组、状态、版本、观察窗口、`product_actions` 证据和回算未知项 | 没有完整观察窗口时返回 `partial`，不得把未回算动作标为已完成 |
| 生命周期人工调整 | 商品 ID、版本、连续有效日、季节月份覆盖、`lifecycle_profiles` 与历史证据 | 少于 60 个连续有效日返回 `insufficient-data`，仍可人工维护但不得宣称算法结论 |
| 设置更新 | 配置动作、操作者、原因、持久化来源和设置审计证据 | 只改变配置口径和模板，不改写历史事实；非法字段返回 `VALIDATION_ERROR` |
| 周期复盘保存 | 周期类型、周期键、复盘人、人工结论、`period_reviews` 证据 | 复盘结论必须与经营事实区分，不能替代指标证据 |

失败响应也必须包含统一的 `availability=calculation-failed`、`evidence_level=insufficient`、`limitations`、`requestId` 和空的上下文数组。前端只能依据结构化状态控制按钮启用、禁用或隐藏，不得解析错误文案推断能力。

### 20.9 当前项目改造顺序（执行版）

本项目不再按“先做一个页面、再补接口”的方式扩展。所有新增能力按以下顺序落地，后一阶段不得绕过前一阶段的停止条件：

| 阶段 | 先解决什么 | 代码落点 | 停止条件 |
|---|---|---|---|
| P0 数据真相层 | 能取得哪些原始字段、覆盖哪些日期、哪些指标可计算 | `services/field_catalog.py`、`services/metric_definitions.py`、`services/data_capability_service.py`、`docs/FIELD_DICTIONARY.md` | 每个数据域都有来源表、粒度、覆盖范围、缺失前提和证据等级；禁止用默认 0 伪造结论 |
| P1 能力注册层 | 页面到底能做什么、依赖什么、缺什么时如何降级 | `services/page_capability_service.py`、`api/page_capabilities_api.py`、`frontend/ui_demo/assets/api.js` | 页面、能力、正式 API、弹窗 `SurfaceDefinition` 一一对应；`unclassified=0`；按钮由 capability 状态统一门禁 |
| P2 经营闭环层 | 从事实到动作再到结果和复盘 | `api/imports_api.py`、`api/goals_api.py`、`api/actions_api.py`、`api/lifecycle_api.py`、`api/period_reviews_api.py` | 导入→总览→商品/推广→动作→观察窗口→回算→复盘链路可追溯，写入接口返回证据和审计信息 |
| P3 旧接口收口层 | 保留兼容的同时，停止让正式页面依赖语义不清的裸接口 | `api/catalog_mutations_api.py`、`api/overview_events_api.py`、`api/schedules_api.py`、`api/manage_api.py`、`api/data_api.py` 旧写接口、各页面 `*-live.js` | 新页面只调用正式域接口；旧接口只供历史深链接和迁移期兼容，并标记 `legacy`，不得再新增业务逻辑 |
| P4 发布门禁层 | 发布前证明代码、数据、运行环境都可用 | `scripts/browser_prd_gates.cjs`、`scripts/production_preflight.py`、测试目录 | 单测、JS 语法、UI 静态校验、浏览器门禁、生产预检全部通过；报告明确区分代码存在、本地验证、数据就绪、正式发布 |

P0/P1 是所有新功能的前置门禁；没有数据证据或能力注册时，只能登记为 `unsupported`，不得先做可点击但没有真实语义的页面。P3 不要求一次性破坏旧接口，采用“新增正式接口、迁移正式页面、最后冻结旧接口”的顺序，确保兼容性可回滚。

当前实现状态：P0、P1、P2 已进入可回归验证；P3 已完成商品元数据/收藏/批量更新/批量打标、总览事件、定时任务、管理任务和用户 KPI 的正式域接口迁移，旧接口继续兼容；P4 已有自动化门禁。后续新增页面不得再直接调用 `api/data_api.py` 中的兼容写接口，迁移工作以新增正式域能力为边界。

### 20.10 多源数据优先级与 DMP 回退规则

TM 的多源数据不能按“整张表覆盖”处理，必须按 `shop_id + product_id + stat_date + standard_key` 的字段级业务键裁决。每个来源同时保留原始观测值，页面和指标只读取裁决后的生效值。

#### 20.10.1 来源角色

| 来源 | 主要职责 | 默认角色 |
|---|---|---|
| 生意参谋 | 商品身份、交易结果、商品主流量 | 主来源 |
| 推广工具 | 推广消耗、付费流量、推广归因成交和 ROI | 主来源 |
| DMP 全店单品列表 | 商品日度补充、流量结构、预售、复购、连带购买 | 参考来源；主来源缺失时按字段回退 |
| 其他报表 | 退款、评价、市场等独立数据域 | 仅对其声明负责的字段生效 |

DMP 不是整表低优先级，也不是整表覆盖来源。一个 DMP 批次中的字段可以分别处于 `reference_only`、`fallback_filled` 或 `effective_unique` 状态。

#### 20.10.2 字段裁决矩阵

| 字段组 | 主来源 | DMP 行为 | 说明 |
|---|---|---|---|
| 商品 ID、商品名称、支付金额、商品 IPV | 生意参谋 | 主源为空时补齐 | 主源有值时 DMP 只保留参考值 |
| 推广消耗、营销推广 IPV、推广 ROI、推广成交 | 推广工具 | 推广工具缺失时补齐 | 不得用 DMP 覆盖推广工具 |
| 退款金额、成功退款金额 | 退款报表/生意参谋 | 不提供主来源 | DMP 没有退款字段，不得推算 |
| 搜索 IPV、推荐 IPV、非推广 IPV、免费搜索点击率 | 专门流量来源 | 无更高等级来源时生效 | 页面标记 DMP 来源 |
| 预售金额、预售销量 | 专门预售来源 | 无其他来源时生效 | DMP 可作为正式可用值 |
| 复购率、复购用户数 | 可去重客户来源 | 无其他来源时生效 | 商品级数据不得汇总成店铺去重买家 |
| 连带购买量、连带购买率、类目宽度 | 专门关联购买来源 | 无其他来源时生效 | 先校验粒度和范围 |
| 支付转化率、笔单价、推广 ROI | 公式计算 | 依赖缺失时参考/回退 | 依赖齐全时禁止直接使用来源比例 |

#### 20.10.3 生效值算法

1. 先按来源和字段写入原始观测，不直接覆盖其他来源的值。
2. 对每个业务键按字段优先级选择第一个非空值；`0` 是有效值，不视为空。
3. 生意参谋和推广工具的主源字段优先于 DMP；DMP 仅在主源字段缺失时回退。
4. DMP 独有字段在无其他来源时可直接生效，并标记 `effective_unique`。
5. 比率、ROI、单价优先使用分子/分母计算；只有依赖字段不足时才使用 DMP 原始比率，并标记 `reference_formula` 或 `fallback_ratio`。
6. 同一字段存在多个非空来源时保留差异，生成对账记录，不静默丢弃。

默认冲突阈值如下，阈值应进入设置或来源配置，不得散落在页面代码中：金额为 `max(1 元, 0.1%)`，数量为 `max(1, 1%)`，比例为 `0.5 个百分点`，ROI 为 `max(0.1, 5%)`。超过阈值显示对账异常，但不阻断主来源入库。

#### 20.10.4 DMP 数据质量门禁

- DMP 文件按 `shop_id + product_id + date` 唯一；本次文件粒度为商品日度，未显式提供店铺时写入 `default`。
- `宝贝ID = 总计`、商品 ID 为空或日期为空的汇总行不得进入商品事实表。
- `-`、`--`、空白和无法解析值按缺失处理，不转换为 0。
- 百分比统一归一化为小数。可选比例或可选数值字段解析失败、超出 `0..1` 时，仅隔离该字段并记录 `field_warnings`，不得因此拒绝整行或整批，也不得截断为 100%。
- 日期、商品 ID、支付金额、商品访客数等必填字段错误仍按行阻断；重复业务键仍按批次阻断。
- 总计行只可用于店铺对账展示，不能参与商品明细汇总。
- 导入报告必须显示总行数、剔除汇总行数、有效行、字段告警数、重复键、日期范围、商品数、冲突数、DMP 补齐数和参考字段数；字段告警至少包含行号、标准字段、原始值和原因。

#### 20.10.5 导入与页面交互

导入预览必须展示“主源值、推广值、DMP 值、最终值、裁决原因”。裁决结果至少包括 `primary_kept`、`fallback_filled`、`reference_only`、`effective_unique`、`conflict`。

商品运营和商品详情页默认展示最终生效值；用户可通过来源筛选查看生意参谋、推广工具、DMP 补齐和 DMP 参考数据。每个指标都必须能查看来源批次、文件名、业务日期、原始值、最终值和裁决原因。

API 的事实类响应增加：`field_source`、`source_role`、`fallback_used`、`conflict_status`、`source_batch_id`。缺少主源而使用 DMP 时，响应和页面必须明确显示“DMP 补齐”，不得伪装成主源数据。

#### 20.10.6 数据存储边界

保留现有 `daily_data` 作为生效事实表，其唯一业务键必须为 `shop_id + product_id + date`；历史库迁移时旧数据归入 `default` 店铺并保持行数不变。新增能力必须另存来源观测和字段血缘，不得为了实现优先级而删除或覆盖历史来源。`daily_data_observations`、`fact_field_lineage` 和 `reconciliation_results` 必须使用同一店铺业务键，支持按字段追溯和按店铺批次撤销。

#### 20.10.7 验收标准

1. 同一商品日期同时存在三方支付金额时，页面采用生意参谋值，DMP 值仍可追溯。
2. 同一商品日期同时存在推广消耗时，页面采用推广工具值，不被 DMP 覆盖。
3. 主来源字段为空且 DMP 有值时，最终值使用 DMP，并显示 `fallback_used=true`。
4. 主来源字段为 0 且 DMP 非 0 时，最终值仍为 0。
5. DMP 独有字段可以进入分析，但来源必须显示为 DMP。
6. 比率和 ROI 依赖字段齐全时按公式重算，不平均来源比率。
7. 重复导入同一 DMP 文件保持幂等，不产生重复业务事实。
8. 冲突、补齐、参考和汇总行剔除均可在数据中心审计。
9. DMP 单行某个比例异常时，其他有效字段正常入库，异常字段不进入观测和有效血缘，导入报告记录字段告警。
10. 两个店铺相同商品同一天的数据分别保留，任一店铺批次撤销不得删除或覆盖另一店铺事实。

该规则适用于总览、商品运营、推广分析、生命周期、导出和运营动作回算；任何页面不得自行定义第二套来源优先级。

## 21. 高级分析能力边界与演进

本节补充 `overview.industry_benchmark` 与 `promotion.causal_attribution` 的产品化边界。两项能力必须根据数据证据分阶段开放，不得把行业参考或推广归因的相关性结果直接表述为排名、增量或严格因果结论。

### 21.1 行业参考基准（`overview.industry_benchmark`）

#### 当前版本：条件可用的行业参考

该能力前台名称统一为“行业参考基准”，不使用“行业排名”“竞品排名”等表述。现有 `/api/industry_benchmark` 已可返回店铺 CTR、行业平均 CTR、差值、差异百分比及最近六个周期趋势；正式前台应在接口返回可用且证据等级足够时展示，否则显示“暂无行业基准数据”。

前台能力包括：

- 总览页展示店铺 CTR 与行业平均 CTR 的并列卡片；
- 展示领先/落后差异、最近六期趋势和当前比较周期；
- 根据差异生成规则化诊断提示，例如 CTR 低于行业参考时提示检查主图、标题和投放人群；
- 展示基准来源、数据覆盖周期、最新更新时间、样本或汇总口径（接口未提供时不得伪造）；
- 允许从总览跳转到推广分析，继承日期范围和推广渠道筛选。

当前版本明确不提供：行业排名、百分位、类目排名、竞品明细和销售额预测。若接口只有行业 CTR 而没有类目、样本量、排名或竞品事实，能力状态只能为 `conditional`。

升级为更完整的行业对标前，必须补充：类目/行业维度、基准样本量、基准来源批次、覆盖周期、可比口径以及必要的分位数或排名数据；补齐后才允许增加 CVR、ROI、退款率等其他指标的基准对比。

### 21.2 推广贡献拆解（替代直接开放 `promotion.causal_attribution`）

#### 当前版本：非因果的推广贡献分析

当前推广数据包含展现、点击、买家数、推广花费、直接成交金额、间接成交金额，并覆盖渠道、计划、单元和商品粒度。这些字段足以支持“推广贡献拆解”，不足以证明“如果没有投放会少卖多少”。

当前版本新增产品语义能力 `promotion.contribution_analysis`，状态为 `conditional`，前台名称统一为“推广贡献分析”。能力包括：

- 直接成交、间接成交、付费成交占比和未归因成交的构成展示；
- 按渠道、计划、单元、商品下钻，展示花费、成交、ROI、CTR、CVR 和贡献占比；
- 展示贡献结构随周期的变化，并支持与推广预警联动；
- 显示归因覆盖率、缺失字段、数据截止日期和限制说明；
- 支持导出当前筛选范围的贡献拆解结果；
- 对“未提供归因”或数据覆盖不足的记录单独展示，不使用 0 替代缺失值。

当前版本禁止使用以下文案或指标：增量成交、真实增量 ROI、因果贡献、投放带来的净新增销售。`direct_payment_amount` 与 `indirect_payment_amount` 只能描述报表归因构成，不能等同于实验意义上的增量。

### 21.3 严格因果评估的开放条件（保留 `promotion.causal_attribution`）

`promotion.causal_attribution` 继续登记为 `unsupported`，直到同时具备以下数据前提：

- 投放曝光或处理记录，包含明确的开始时间和结束时间；
- 可识别的实验组与对照组，或可审计的准实验设计；
- 统一的投放前基线、观察窗口和结果指标；
- 自然流量、价格、活动、库存、商品状态等主要干扰因素；
- 能追溯到来源批次、样本范围和分析版本的审计记录。

满足条件后，才可设计实验因果评估页面，提供投放增量成交、增量 ROI、对照组差异、置信区间和敏感性说明。页面必须同时展示设计类型、样本量、观察窗口、缺失数据和不能解释的范围；任何结果都不能脱离实验设计单独展示为事实。

### 21.4 前台页面与发布顺序

| 阶段 | 前台能力 | 页面位置 | 发布条件 |
|---|---|---|---|
| P0 | 行业参考基准 | 总览 KPI 区与趋势区 | 行业 CTR 字段可用，接口返回来源、覆盖周期和证据等级 |
| P0 | 推广贡献分析 | 推广分析新增“贡献分析”视图 | 推广事实至少具备粒度、花费、成交和归因覆盖状态 |
| P1 | 基准数据与归因数据目录 | 数据中心能力详情 | 能查看来源表、字段可用性、覆盖范围和限制 |
| P2 | 严格因果评估 | 推广分析实验评估页 | 实验/对照设计和审计数据全部满足 21.3 前置条件 |

能力注册要求：在 P0/P1 完成前，`overview.industry_benchmark` 只能按 `conditional` 或 `unsupported` 返回；新增 `promotion.contribution_analysis`，并保持 `promotion.causal_attribution` 为 `unsupported`。所有按钮、弹窗和导出入口必须通过统一 capability 状态门禁。

### 21.5 API 与证据契约

- `/api/industry_benchmark` 正式接入前台时必须补齐统一 envelope、`availability`、`evidence_level`、`freshness`、`missing_inputs` 和 `limitations`；不能让前台根据裸 JSON 是否有值自行判断可用性。
- `/api/promotion` 返回的贡献拆解必须保留来源批次、粒度、筛选条件和缺失范围；`direct_payment_amount`、`indirect_payment_amount`、`attributed_payment_amount` 的定义必须在字段字典中保持一致。
- 贡献分析导出必须使用当前筛选、字段模板和数据口径，并在导出文件中写入“非因果归因”说明。
- 数据证据不足时，前台只显示可用数据和限制，不生成默认行业值、默认贡献值或因果结论。
