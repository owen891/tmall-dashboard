# 边界 BI 能力复刻规划

**版本**：v1.0  
**日期**：2026-09-21  
**适用项目**：tmall-dashboard  
**规划目标**：复刻边界 BI 在商品经营场景中的核心功能与能力，不以页面外观或导航结构复刻为目标。

## 1. 复刻原则

本规划以实际探测到的两个页面为依据：

- 商品总览：商品规则分群、经营问题识别、商品集合下钻、商品列表运营。
- 商品运营分析：单商品工作台、主题化分析、推广渠道拆解、指标明细与计划下钻。

复刻对象分为四层：

1. **数据能力**：字段、口径、时间粒度、来源、覆盖范围和数据质量。
2. **分析能力**：规则分群、指标计算、对比、趋势、贡献和下钻。
3. **运营能力**：筛选、选款、跟进、待办、负责人、标签、视窗和导出。
4. **决策闭环**：发现问题、定位商品、分析原因、创建动作、观察结果、复盘验证。

复刻时坚持以下边界：

- 只复刻有真实数据依据的能力；缺字段时显示不可用原因，不用 0 代替。
- 每个指标必须带统计口径、数据来源、时间范围和对比方式。
- 所有规则卡片必须能还原为可审计的筛选条件。
- 所有跨页下钻必须通过 URL 或可恢复状态传递上下文。
- 先保持 Flask 多页面和原生 JavaScript 架构，不因复刻 BI 直接迁移 React/Vue。

## 2. 目标产品结构

### 2.1 商品经营入口

目标页面：`/products` 与 `product-detail`。

首屏应形成以下路径：

```text
时间范围
  -> 经营分群卡片
      -> 商品集合
          -> 商品列表筛选/排序
              -> 单商品工作台
                  -> 主题分析
                      -> 运营动作与结果观察
```

### 2.2 商品总览能力

商品总览由五个区域组成：

1. **统计上下文**
   - 日、周、月、自定义时间范围。
   - 当前周期、上一周期、同比周期。
   - 数据截止时间、覆盖天数、数据来源和数据质量。

2. **经营分群卡片**
   - 全部商品。
   - 高毛利盈利单品。
   - 低毛利战略单品。
   - 高付费高退款。
   - 亏损链接。
   - 低/中/高客单价。
   - 高转化亏损。
   - 高搜索亏损。
   - 高加购零付费。
   - 利润下降/增长。
   - 费比下降。

3. **卡片规则解释**
   - 显示规则名称。
   - 显示完整条件。
   - 显示指标口径。
   - 显示命中数量、占比、环比。
   - 显示空结果、数据不足和计算失败的区别。

4. **商品经营列表**
   - 商品、店铺、类目、上架时间。
   - 净销售额、推广花费、推广占比。
   - 利润、利润率、访客、支付转化率。
   - 客单价、加购率、搜索访客占比。
   - 退款率、毛利率、单次付费访客成本。
   - 跟进、待办、负责人、有效类目、盈亏状态。

5. **视图与运营操作**
   - 选款视图。
   - 列表视图。
   - 周期视图。
   - 大图视图。
   - 字段模板和个人视窗。
   - 收藏、批量打标、批量分层、批量创建动作。
   - 导出当前筛选结果。

### 2.3 商品运营分析能力

目标页面：现有 `/product-detail` 工作台，逐步扩展为单商品分析中心。

顶部固定展示：

- 商品主图、商品标题、商品 ID。
- 店铺、标准类目、上架时间。
- 当前周期和数据截止时间。
- 商品标签、跟进状态、待办数量、未读消息。
- 切换商品入口。

分析主题分为：

1. **总览数据**
   - 销售、利润、成本、流量、转化、退款和推广汇总。
   - 当前周期、上一周期、同比和自定义对比。
   - 经营结论和异常指标。

2. **流量来源**
   - 搜索、推荐、付费、活动、私域及其他来源。
   - 访客、支付买家、支付金额、转化率、客单价。
   - 来源占比、环比变化、来源贡献。

3. **搜索分析**
   - 搜索访客、搜索访客占比、搜索点击率。
   - 关键词、展现、点击、点击率、成交和转化。
   - 高流量低转化、高转化低流量关键词分组。

4. **标题优化**
   - 标题当前版本、历史版本、变更记录。
   - 关键词覆盖、搜索贡献和风险提示。
   - 变更动作与观察窗口关联。

5. **推广分析**
   - 展现、点击、花费、点击率、点击转化率。
   - 平均点击单价、千次展现花费。
   - 成交额、成交笔数、加购数、收藏数。
   - ROI、直接成交 ROI、间接成交 ROI。
   - 花费/笔数、花费/直接笔数、花费/间接笔数。
   - 关键词推广、精准人群推广等渠道分区。
   - 计划状态、花费占比和计划详情下钻。

6. **SKU 分析**
   - SKU 销量、销售额、利润、退款。
   - 颜色、尺码、组合和库存关联。
   - SKU 贡献排序和异常 SKU。

7. **地域分析**
   - 地域访客、成交、转化、客单和利润。
   - 高成交低利润地区、高流量低转化地区。

8. **时段分析**
   - 小时级访客、点击、成交、转化和花费。
   - 高峰时段、低效时段和投放建议。

## 4. 数据层规划

### 4.1 统一数据域

保留现有数据能力目录，并补充以下正式数据域：

- `product_daily`：商品日经营事实。
- `product_monthly`：商品月经营事实。
- `store_daily`：店铺日经营事实。
- `promotion_daily`：推广日事实。
- `promotion_campaign`：推广计划事实。
- `promotion_keyword`：关键词计划或关键词明细。
- `promotion_audience`：人群计划明细。
- `product_sku_daily`：SKU 日经营事实。
- `product_region_daily`：商品地域日事实。
- `product_hourly`：商品时段事实。
- `product_rule_snapshot`：规则命中快照。
- `product_view_template`：字段模板和个人视窗。

### 4.2 核心字段要求

每个事实字段必须具备：

- `field_key`
- `label`
- `unit`
- `grain`
- `aggregation`
- `formula`
- `source`
- `source_field`
- `availability`
- `missing_inputs`
- `coverage_start`
- `coverage_end`
- `updated_at`

### 4.3 重点口径

统一以下指标定义：

- 净销售额：支付金额扣除成功退款，具体以当前数据源口径为准。
- 推广花费：区分账单口径和支付预估口径。
- 利润：优先使用 BI 已提供的利润字段；没有真实利润字段时，只能显示“不可用”或明确标注推导口径。
- 利润率：利润 / 净销售额，分母为 0 时不可计算。
- 推广占比：推广花费 / 净销售额。
- ROI：归因成交额 / 推广花费。
- 环比：当前周期与等长上一周期比较。
- 同比：当前周期与上一年度同周期比较。

任何字段缺失时：

- `missing-fields`：缺少计算所需字段。
- `partial`：部分日期、商品或渠道可用。
- `no-data`：查询范围内无数据。
- `calculation-failed`：字段存在但计算失败。
- `source-unavailable`：来源不可用。

## 5. 规则引擎规划

不要把规则写死在页面脚本中，建立规则注册表：

```text
rule_key
name
group
description
conditions
metric_key
period_mode
compare_mode
severity
enabled
sort_order
```

规则条件采用结构化表达式，例如：

```json
{
  "all": [
    {"field": "net_product_cost_ratio", "operator": "<=", "value": 0.30},
    {"field": "promotion_ratio", "operator": "<=", "value": 0.30}
  ]
}
```

规则执行结果必须返回：

- 命中商品数量。
- 命中商品 ID。
- 规则版本。
- 参与计算商品数量。
- 不可计算商品数量。
- 触发字段缺失数量。
- 当前周期和对比周期结果。

## 7. 前端实施规划

### 阶段 A：统一上下文和入口

- 统一日期范围、对比方式和 URL 参数。
- 增加商品总览上下文栏。
- 统一卡片、表格、字段模板和数据状态组件。
- 明确商品列表与商品详情的下钻协议。

**验收**：

- 日期切换后所有卡片、列表和详情使用同一范围。
- 刷新、前进、后退能够恢复上下文。
- 不同页面不会静默修改或丢失筛选条件。

### 阶段 B：商品总览复刻

- 建立规则注册表和规则结果接口。
- 用经营规则卡片替换单纯 KPI 展示。
- 卡片点击进入商品列表，并自动带入规则筛选。
- 商品列表补齐跟进、待办、负责人、视窗和多视图。
- 增加规则说明、数据质量和空结果状态。

**验收**：

- 每张规则卡片都能打开对应商品集合。
- 页面展示的数量与列表总数一致。
- 列表可以回到规则卡片上下文。
- 规则条件可复制、可审计、可复现。

### 阶段 C：单商品工作台复刻

- 将现有 product-detail 改为主题化工作台。
- 先实现总览、流量来源、搜索、推广四个主题。
- 推广分析按渠道拆分计划表和指标矩阵。
- 每个主题支持当前周期、对比周期、更多字段和导出。
- 将跟进、待办、动作和观察窗口放入商品上下文。

**验收**：

- 从总览商品列表进入后，商品 ID、日期和筛选上下文不丢失。
- 四个主题切换不重复请求无关数据。
- 推广总计与渠道汇总可校验。
- 缺失字段时不显示虚假的 0 或利润值。

### 阶段 D：深度分析

- SKU 分析。
- 地域分析。
- 时段分析。
- 标题版本和关键词覆盖分析。
- 规则命中历史和异常变化。

**验收**：

- 每个新主题先通过数据能力检查，再显示为可用入口。
- 没有对应数据域时显示不可用原因。
- 新增主题不影响已上线主题的接口和页面状态。

### 阶段 E：运营闭环

- 从规则卡片或指标异常创建运营动作。
- 动作绑定商品、问题类型、目标指标和观察窗口。
- 到期后自动计算前后指标变化。
- 在商品详情、概览运营中心和复盘页统一展示结果。

**验收**：

- 每个动作能追溯到触发规则和原始指标。
- 动作状态可从待处理到观察中、待复盘、已完成。
- 结果计算失败时保留失败原因和重试入口。

## 9. 测试与验收矩阵

### 数据与后端

- 指标公式和聚合方式测试。
- 日期、周期、同比和环比测试。
- 规则条件解析和命中结果测试。
- 缺失字段、部分覆盖、无数据测试。
- 推广总计与渠道汇总一致性测试。
- 商品列表筛选和卡片下钻一致性测试。
- 导出结果与当前筛选一致性测试。

### 前端契约

- 页面必须声明所有数据状态区域。
- 页面必须声明主题 Tab、下钻入口和返回入口。
- 所有 URL 参数必须经过统一导航白名单。
- 字段模板、视窗、筛选和分页必须可恢复。
- 弹窗、抽屉和详情区域必须声明 modal kind。

### 浏览器场景

1. 七天商品总览加载。
2. 点击“亏损链接”进入商品列表。
3. 列表筛选后进入商品详情。
4. 商品详情切换总览、流量、搜索、推广。
5. 推广渠道表展开计划详情。
6. 数据缺失时验证不可用状态。
7. 切换日期后返回浏览器前进/后退。
8. 移动端查看商品摘要和详情入口。
9. 连续切换主题 10 次，检查图表实例不累积。
10. 导出当前筛选结果并校验字段口径。

## 10. 优先级与交付顺序

### P0：先形成可用闭环

- 统一时间和数据状态。
- 商品规则分群卡片。
- 规则卡片到商品列表下钻。
- 商品详情总览、流量、搜索、推广。
- 跟进、待办、运营动作贯通。
- 利润、成本、推广口径校准。

### P1：提升分析效率

- 个人视窗和字段模板。
- 推广渠道计划拆解。
- 关键词、标题优化联动。
- SKU 分析。
- 导出、规则配置和规则历史。

### P2：扩展经营深度

- 地域分析。
- 时段分析。
- 规则自动推荐。
- 异常订阅和连续下滑预警。
- 商品、类目、店铺多层级联动。

## 11. 不建议复刻的内容

- 不复刻 BI 的品牌、水印、视觉细节和固定布局。
- 不在没有数据支撑时伪造地域、时段或 SKU 分析。
- 不把所有 800+ 原始字段直接搬到首屏。
- 不把规则条件只写在前端文本中。
- 不用“更多数据”替代字段目录、指标说明和真实数据状态。
- 不建立与现有产品、推广、生命周期和动作系统平行的第二套数据口径。

## 12. 最终交付标准

完成本规划后，用户应能完成以下闭环：

```text
我发现哪些商品有问题？
  -> 为什么这些商品被归入这个问题？
  -> 具体是哪批商品？
  -> 单个商品的问题来自流量、搜索、推广、SKU、地域还是时段？
  -> 我做了什么动作？
  -> 动作后指标是否改善？
  -> 证据和口径是否可复核？
```

这才是对边界 BI 的能力复刻；页面样式和导航只是承载这些能力的外壳。

## 13. 深度分析：边界 BI 的真正产品结构

### 13.1 它不是仪表盘，而是商品决策操作系统

商品总览页面表面上是“卡片 + 表格”，商品运营分析页面表面上是“Tab + 指标 + 表格”，但它们实际承担的是一套连续的决策流程：

```text
规则识别问题
  -> 形成商品集合
    -> 筛选和排序
      -> 选定单品
        -> 按主题拆解原因
          -> 形成跟进/待办
            -> 记录动作并观察结果
```

因此复刻的最小单位不是页面，而是一个**可追踪的经营问题对象**。这个对象至少要记录：

- 问题类型：亏损、低毛利、高退款、低转化、费比上升等。
- 触发规则：字段、运算符、阈值和规则版本。
- 商品范围：命中商品、参与计算商品、不可计算商品。
- 时间范围：当前周期、对比周期和数据截止日。
- 诊断证据：流量、搜索、推广、SKU 等明细。
- 后续动作：负责人、计划日期、目标指标、观察窗口。
- 结果：动作前后指标、变化值、复盘结论。

如果缺少这个问题对象，系统只能提供“看数”，不能提供“经营决策”。

### 13.2 商品总览页面的核心是集合运算

BI 的经营卡片不是普通 KPI 卡片，而是对商品集合执行的业务规则：

```text
商品全集
  -> 过滤有效数据
  -> 计算派生指标
  -> 执行规则
  -> 生成命中集合
  -> 计算集合数量、占比、环比
```

这带来三个重要要求：

1. **规则结果必须稳定**
   - 同一日期、同一规则版本、同一数据快照，应得到同一商品集合。
   - 页面不能根据当前表格分页结果临时计算卡片数量。

2. **分母必须明确**
   - “占比”是占全部商品、有效商品，还是有该指标数据的商品，必须显式标注。
   - 规则不可计算的商品不能悄悄进入分母或被当成 0。

3. **卡片与列表必须共用查询定义**
   - 卡片数量、列表总数和导出总数必须来自同一套条件表达式。
   - 不能出现卡片显示 503 个、点击后列表却筛出另一批商品的情况。

当前项目已经有商品筛选和数据状态能力，但商品规则还没有成为统一的一等对象。这是 P0 的真正原因。

### 13.3 商品运营分析页面的核心是主题化诊断

BI 没有把所有字段放在一个超宽表中，而是按经营问题拆分主题：

| 主题 | 回答的问题 | 关键事实 |
| --- | --- | --- |
| 总览 | 这个商品现在结果如何 | 成交、利润、成本、流量、转化 |
| 流量来源 | 用户从哪里来 | 来源、访客、支付、转化、UV 价值 |
| 搜索分析 | 搜索入口是否有效 | 关键词、展现、点击、成交 |
| 标题优化 | 内容是否匹配需求 | 标题版本、词覆盖、搜索贡献 |
| 推广分析 | 付费流量是否值得 | 计划、渠道、ROI、直接/间接成交 |
| SKU 分析 | 哪个规格贡献或拖累结果 | SKU 销售、利润、退款、库存 |
| 地域分析 | 哪些地域值得经营 | 地域流量、成交、转化、利润 |
| 时段分析 | 什么时候投放或经营 | 小时级流量、成交、花费 |

每个主题都应有独立的：

- 数据源。
- 指标集合。
- 默认排序。
- 诊断规则。
- 空数据和缺字段状态。
- 下钻路径。

这比在商品详情页继续增加 KPI 卡片更重要。

### 13.4 “更多数据”和“卡片设置”体现的是字段产品能力

BI 的“更多数据”“卡片设置”“个人视窗/默认视窗”不是装饰性配置，它解决的是两类冲突：

- 管理者需要少量结论指标。
- 分析人员需要完整字段和自定义排序。

因此我们需要区分三层字段：

1. **核心指标**：页面默认展示，保证判断路径稳定。
2. **诊断字段**：按主题开放，支持定位原因。
3. **原始证据字段**：用于核对来源、口径和异常。

当前项目已有字段选择器和模板管理，但主要还是“表格列配置”。下一步应将模板升级为：

- 按页面主题隔离。
- 绑定字段版本和口径说明。
- 记录创建人和更新时间。
- 保存默认排序、筛选和分组。
- 在导出时带上字段定义和数据来源。

### 13.5 BI 的标签本质上是“预计算经营语言”

“高毛利盈利单品”“高搜索亏损”“利润下降 30% 的链接”把原始指标转换成运营人员可以直接行动的语言。

这类标签有四种价值：

- 降低用户理解指标的成本。
- 把经验规则标准化。
- 直接形成商品集合。
- 为动作和复盘提供问题类型。

但标签不能只存在于页面文案中。需要保存：

```text
rule_key
rule_version
rule_label
rule_expression
evaluated_at
data_snapshot
matched_product_count
```

这样才能回答“为什么这个商品被归类为亏损链接”，也才能在规则调整后比较前后命中变化。

## 14. 当前项目的真实差距

### 14.1 已经具备的底座

当前项目并不是从零开始，已经有：

- `daily_data`、`monthly_data` 和 `promotion_daily_facts` 等经营事实。
- `product-detail` 商品工作台和 KPI 下钻。
- `promotion` 页面中的渠道、计划、商品、关键词、人群、创意和站内渠道视图。
- `flow-source` 的流量来源分析。
- `lifecycle` 的阶段判断和历史。
- `product_actions` 的动作状态、观察窗口和结果复盘。
- `data_capability_service` 的 availability、evidence 和覆盖范围。
- 字段选择器、字段模板、数据中心和导入审计。

这些底座足以支持 P0 复刻，不需要新建一套平行产品。

### 14.2 关键结构性缺口

#### 缺口一：没有统一的商品经营上下文

现在日期状态由 shell 维护，商品筛选由 products 维护，推广查询由 promotion 维护，商品详情又单独读取日期状态。它们可以分别工作，但还没有统一的上下文对象：

```text
shop_id
product_id / product_set_id
start_date
end_date
compare_mode
compare_start
compare_end
rule_key
rule_version
view_id
```

没有统一上下文，就无法可靠实现“从卡片进入列表，再进入单品，再返回原问题”的路径。

#### 缺口二：规则能力与告警能力没有分层

当前项目已有 `alert_rules`，但 BI 商品卡片属于“经营分群”，不是简单的通知预警。两者应区分：

- 分群规则：用于形成商品集合和页面入口。
- 预警规则：用于产生待处理通知。
- 诊断规则：用于解释问题原因。
- 动作规则：用于建议下一步操作。

它们可以复用条件表达式，但不能共用同一个页面语义。

#### 缺口三：商品详情已有数据，但主题边界还不完整

当前商品详情已经有经营概览、日度趋势、流量来源、生命周期、运营动作和数据证据，这个方向正确。但与 BI 的主题工作台相比，还缺：

- 商品级搜索词与标题优化联动。
- 商品级推广总览与渠道计划拆解的一致入口。
- SKU 经营数据的正式数据域。
- 地域和时段数据域。
- 每个主题独立的对比、排序和诊断规则。

优先补齐主题边界，不要继续把所有指标添加到“经营概览”。

#### 缺口四：推广数据已有粒度，但需要统一归因语义

当前 `promotion_daily_facts` 已支持渠道、计划、单元、商品等粒度，且有 `promotion_campaign_items` 作为计划与商品映射。这是复刻 BI 推广分析最有价值的底座。

但必须严格区分：

- 渠道报告汇总。
- 计划报告汇总。
- 商品报告汇总。
- 商品链接经营结果。
- 直接成交和间接成交。

这些粒度不能简单相加，否则会把同一笔成交重复计入。推广页面已经有“不重复汇总”的设计提示，后续应把它提升为后端查询契约。

#### 缺口五：当前指标注册表仍偏店铺和基础商品指标

`metric_definitions.py` 已经建立统一公式，但主要覆盖净销售、退款率、转化率、客单价、费比、ROI 和老客占比。复刻 BI 还需要扩展：

- 商品成本和利润口径。
- 毛利、毛利率、利润率。
- 推广占比。
- 直接/间接成交。
- 展现、点击、CTR、CPC、CPM。
- 加购、加购率、加购成本。
- 收藏、收藏率。
- 新客、拉新成本。
- 单次付费访客成本和单次付费访客利润。

扩展时要先定义依赖字段和粒度，不能只增加显示字段。

## 15. 推荐的产品重构模型

### 15.1 用“问题中心”连接页面

建议新增一个轻量的问题中心概念，而不是新增一个孤立页面：

```text
ProblemSet
  id
  rule_key
  rule_version
  title
  period
  compare_period
  product_count
  data_quality
  created_at
```

它可以由规则实时生成，也可以按周期保存快照。页面表现为：

- 总览上的经营卡片。
- 商品列表上的已应用规则摘要。
- 商品详情上的命中原因。
- 运营动作上的触发来源。
- 复盘页上的问题变化。

### 15.2 用“主题能力协议”统一单品分析

每个商品分析主题都采用同一协议：

```text
主题 key
  -> context
  -> metrics
  -> trend
  -> breakdown
  -> rows
  -> diagnosis
  -> evidence
```

前端 Tab 只负责切换主题，后端负责返回主题自己的能力状态。这样可以避免每个 Tab 都重新发明数据状态、字段说明和导出逻辑。

### 15.3 用“证据链”替代孤立数值

单个指标不能只返回 value，至少返回：

```json
{
  "key": "roi",
  "value": 2.73,
  "unit": "ratio",
  "formula": "attributed_payment_amount / ad_spend",
  "basis": "promotion_campaign",
  "grain": "product_day",
  "source_fields": ["attributed_payment_amount", "ad_spend"],
  "coverage": {"start": "2026-09-14", "end": "2026-09-20"},
  "availability": "available"
}
```

这会直接解决当前项目中“数字存在，但用户不知道口径和来源”的问题。

## 16. 实施决策：先做什么，暂时不做什么

### 16.1 第一阶段必须完成

1. 统一商品经营上下文。
2. 建立商品规则注册表。
3. 把规则卡片、商品列表和商品详情连成一条可返回的链路。
4. 扩展基础指标注册表和利润/成本数据状态。
5. 将推广主题与商品详情统一。
6. 将问题触发来源写入运营动作。

### 16.2 第二阶段再做

- 商品级搜索词和标题版本。
- SKU 数据域和组合分析。
- 个人视窗升级。
- 规则配置、规则版本和历史快照。
- 当前视图导出和证据导出。

### 16.3 暂不承诺

- 没有稳定数据源之前不承诺地域分析。
- 没有小时级采集之前不承诺时段分析。
- 没有实验或对照设计之前不承诺因果归因。
- 没有库存事实之前不把库存状态伪装成商品经营分析。
- 没有完整市场基准之前不承诺市场机会判断。

## 17. 深度验收标准

除了“页面能打开”，还必须验证以下业务一致性：

### 规则一致性

- 卡片命中数 = 列表总数 = 导出行数。
- 卡片规则说明与后端实际表达式一致。
- 缺失字段商品不被错误计入 0 值命中。

### 口径一致性

- 商品详情推广汇总与推广页商品粒度结果一致。
- 渠道、计划、商品三种粒度不重复求和。
- 当前周期、对比周期和环比标签与 URL 参数一致。

### 上下文一致性

- 从规则卡片进入列表保留规则、时间和对比条件。
- 从列表进入商品详情保留商品、时间和来源规则。
- 返回列表后筛选、页码和视窗可恢复。

### 数据状态一致性

- 页面、指标、表格和导出共享同一 availability。
- `0` 只表示真实零值，不表示缺失。
- `--`、不可计算、暂无数据和来源不可用语义不同。

### 决策闭环一致性

- 每个运营动作可以追溯到问题集合或指标异常。
- 每个复盘结果可以追溯到动作前后的同口径指标。
- 无法计算结果时保留原因，不伪造完成状态。

## 18. 页面排版与功能落位规范

本节解决两个问题：第一，页面如何排版才能承载完整的经营分析路径；第二，用户在每个区域具体能做什么。目标不是照搬 BI 的像素布局，而是复刻它的**信息层级、操作顺序和工作效率**。

### 18.1 总体排版原则

#### 18.1.1 页面采用“上下文固定、内容滚动”

所有商品经营页面统一采用以下结构：

```text
全局导航
  -> 页面标题与面包屑
    -> 上下文工具栏
      -> 页面主体
        -> 数据表格 / 图表 / 诊断结果
```

- 全局导航只负责页面切换，不承载具体分析功能。
- 页面标题区说明当前页面和数据范围。
- 上下文工具栏固定在主体上方，日期、店铺、对比周期和筛选条件始终可见。
- 主体区域独立滚动，不能让用户滚动到底部后失去当前时间范围和筛选状态。
- 商品详情中的商品身份栏在滚动时保持可见，避免用户在长页面中丢失当前商品。

#### 18.1.2 使用三层信息密度

页面内容按决策顺序分成三层：

```text
第一层：结论
  当前发生了什么，影响多大，需要关注什么

第二层：诊断
  哪些商品、渠道、关键词、SKU 或日期造成了结果

第三层：证据
  字段、公式、来源、明细、覆盖范围和原始记录
```

- 首屏只展示核心结论，不堆放所有字段。
- 诊断内容通过卡片、图表、分组表和抽屉展开。
- 证据内容通过“指标说明”“查看明细”“数据证据”进入，不与结论争夺首屏空间。

#### 18.1.3 固定区、可折叠区和滚动区明确分工

| 区域 | 行为 | 适合放置的内容 |
| --- | --- | --- |
| 固定区 | 页面滚动时仍可见 | 时间范围、商品身份、关键操作、返回路径 |
| 可折叠区 | 默认展示摘要，可展开详情 | 规则说明、指标口径、诊断结论、数据质量 |
| 滚动区 | 承载大量数据 | 商品表、计划表、关键词表、SKU 表、趋势明细 |

不得把大型表格、规则解释和所有指标都放入固定区，否则会压缩真正的数据工作区。

### 18.2 商品总览页面排版

商品总览的核心任务是“发现问题并选出商品”，因此排版顺序必须遵循：

```text
先确定范围
  -> 看问题分布
    -> 选择问题集合
      -> 筛选和排序商品
        -> 进入单品分析
```

推荐桌面端结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 页面标题 / 面包屑 / 数据更新时间 / 帮助                      │
├──────────────────────────────────────────────────────────────┤
│ 店铺  日期  对比周期  数据状态  刷新  保存视窗  导出           │
├──────────────────────────────────────────────────────────────┤
│ 已应用条件：类目 / 负责人 / 生命周期 / 规则 / 标签             │
├──────────────────────────────────────────────────────────────┤
│ 经营分群卡片区：问题卡片按组排列，可横向浏览或分行展示         │
├──────────────────────────────────────────────────────────────┤
│ 结果工具栏：商品数 / 当前规则 / 筛选 / 排序 / 视图 / 字段设置   │
├──────────────────────────────────────────────────────────────┤
│ 商品经营列表：冻结商品列，指标列横向滚动，操作列固定           │
└──────────────────────────────────────────────────────────────┘
```

#### 18.2.1 顶部页面标题区

放置：

- 页面名称：商品总览。
- 当前店铺或店铺集合。
- 数据截止时间和最近刷新时间。
- 数据质量提示入口。
- 帮助和口径入口。

功能：

- 返回店铺经营中心。
- 打开数据状态抽屉。
- 查看当前页面的字段和规则说明。

标题区不放置大量 KPI，避免页面一打开就变成第二个概览首页。

#### 18.2.2 上下文工具栏

从左到右保持稳定顺序：

1. 店铺选择。
2. 日期模式：日、周、月、自定义。
3. 当前周期。
4. 对比方式：上一周期、同比、无对比、自定义。
5. 数据状态。
6. 刷新。
7. 保存视窗。
8. 导出。

交互要求：

- 修改日期或店铺后，规则卡片和商品列表一起刷新。
- 对比方式改变后，所有变化值同步重算。
- 刷新按钮显示数据更新时间和请求状态。
- 保存视窗保存时间、规则、筛选、排序、字段和视图模式。
- 导出默认导出当前规则、筛选、排序和字段，不导出隐含的全量数据。

#### 18.2.3 已应用条件条

条件条是连接卡片和列表的关键区域，必须显示：

- 当前规则名称和规则版本。
- 当前筛选条件。
- 当前排序。
- 当前商品集合数量。
- 清除单个条件和全部条件。
- 返回上一个商品集合入口。

当用户从“亏损链接”卡片进入列表时，条件条应显示：

```text
经营分群：亏损链接 v1
时间：2026-09-14 至 2026-09-20
命中：126 个商品
```

规则条件不得只隐藏在接口参数中，用户必须能够看到并打开完整规则说明。

#### 18.2.4 经营分群卡片区

卡片按经营语义分组，而不是全部混排：

| 卡片组 | 典型卡片 | 作用 |
| --- | --- | --- |
| 盈利与利润 | 高毛利盈利、利润增长、利润下降 | 判断利润结果 |
| 成本与风险 | 亏损链接、高付费高退款、费比下降 | 判断经营风险 |
| 流量与转化 | 高转化亏损、高搜索亏损、高加购零付费 | 判断流量质量 |
| 价格带 | 低客单价、中客单价、高客单价 | 判断商品结构 |

单张卡片至少包含：

- 卡片标题。
- 一句话规则描述。
- 命中数量。
- 占有效商品的比例。
- 环比或同比变化。
- 数据可用性状态。
- 查看商品按钮。
- 查看规则按钮。

卡片交互：

- 点击卡片主体：进入对应商品集合。
- 点击数量：进入列表并保留规则上下文。
- 点击规则说明：打开规则抽屉。
- 点击变化值：打开当前周期与对比周期的集合变化。
- 点击更多操作：保存为视窗、创建跟进任务、导出命中商品。

卡片不应承载复杂表格。需要查看商品明细时进入列表或侧边抽屉。

#### 18.2.5 商品列表区

列表采用“左侧身份列 + 中间指标列 + 右侧动作列”的稳定结构：

```text
商品身份 | 经营结果 | 流量转化 | 推广效率 | 风险标签 | 负责人/动作
```

推荐默认字段：

- 商品主图、标题、商品 ID。
- 类目、上架时间、生命周期。
- 净销售额、订单、利润、利润率。
- 访客、支付转化率、客单价。
- 推广花费、推广占比、ROI。
- 退款率、毛利率、异常标签。
- 跟进状态、负责人、待办数。

列表功能：

- 表头排序。
- 多字段筛选。
- 多选商品。
- 批量打标签。
- 批量分配负责人。
- 批量创建运营动作。
- 冻结列和横向滚动。
- 列宽调整。
- 字段显示/隐藏。
- 保存个人视窗。
- 当前结果导出。

商品行交互：

- 点击商品标题：进入商品工作台。
- 点击问题标签：查看命中规则和证据。
- 点击指标：进入该指标对应的主题分析。
- 点击负责人或跟进状态：直接编辑运营状态。
- 点击更多：收藏、创建待办、查看操作历史。

列表不能把所有功能都放进右键菜单，最常用的“详情、跟进、待办”应当在行内可见。

#### 18.2.6 视图模式

四种视图解决不同任务，不能只做皮肤切换：

| 视图 | 默认场景 | 主要信息 |
| --- | --- | --- |
| 选款 | 快速挑选商品 | 主图、标题、核心结果、问题标签 |
| 列表 | 批量运营和对比 | 完整指标、筛选、排序、批量操作 |
| 周期 | 看趋势和变化 | 多周期指标、趋势、变化原因 |
| 大图 | 视觉化浏览商品集合 | 主图、经营标签、核心指标、状态 |

切换视图时保留规则、日期、筛选、排序和选中商品；只改变展示层，不改变查询集合。

### 18.3 商品运营分析页面排版

商品运营分析的核心任务是“定位单品问题并形成动作”，因此页面应采用商品身份固定、主题 Tab 切换、主题内部统一结构的工作台布局。

推荐结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 返回商品集合  商品主图  标题  商品ID  店铺  状态  跟进/待办     │
├──────────────────────────────────────────────────────────────┤
│ 日期  对比周期  数据状态  上一商品 / 下一商品  更多操作         │
├──────────────────────────────────────────────────────────────┤
│ 总览 | 流量来源 | 搜索 | 标题 | 推广 | SKU | 地域 | 时段       │
├──────────────────────────────────────────────────────────────┤
│ 主题结论：异常提示 / 关键指标 / 建议动作                       │
├──────────────────────────────────────────────────────────────┤
│ 趋势区或结构图：当前周期与对比周期                             │
├──────────────────────────────────────────────────────────────┤
│ 明细区：分组表格 / 计划表 / 关键词表 / SKU表                   │
├──────────────────────────────────────────────────────────────┤
│ 证据与动作：指标口径 / 数据来源 / 创建待办 / 观察窗口           │
└──────────────────────────────────────────────────────────────┘
```

#### 18.3.1 商品身份栏

固定展示：

- 商品主图。
- 商品标题。
- 商品 ID。
- 店铺和类目。
- 上架日期。
- 当前命中标签。
- 跟进状态。
- 待办数量。

固定操作：

- 返回商品列表。
- 切换上一个/下一个商品。
- 收藏商品。
- 创建运营动作。
- 打开商品原始链接或外部详情。

从商品总览进入时，身份栏还要显示来源：

```text
来源：经营分群 / 亏损链接 / 2026-09-14 至 2026-09-20
```

这样用户知道为什么正在分析这个商品。

#### 18.3.2 分析主题 Tab

Tab 只负责切换主题，不把所有数据一次性加载。每个 Tab 应具备：

- 可用状态。
- 加载状态。
- 无数据状态。
- 缺字段状态。
- 当前主题的导出入口。
- 当前主题的字段设置。
- 当前主题的诊断说明。

默认顺序：

```text
总览数据 → 流量来源 → 搜索分析 → 标题优化 → 推广分析
→ SKU 分析 → 地域分析 → 时段分析
```

如果某主题的数据域未接入，Tab 可以保留，但必须明确显示“当前数据不可用”和原因，不能进入空白页面。

#### 18.3.3 主题内容的统一排版

每个主题内部遵循四段式：

```text
结论条
  -> 核心指标行
    -> 趋势/结构图
      -> 明细表与证据
```

结论条显示：

- 当前主题最重要的一个结论。
- 影响方向。
- 触发的诊断规则。
- 推荐的下一步动作。

核心指标行控制在 4 至 8 个，按业务顺序排列，不按数据库字段顺序排列。每个指标显示当前值、对比值、变化值和可用状态。

趋势或结构图必须带：

- 当前周期和对比周期图例。
- 单位和时间粒度。
- 数据点为空时的明确原因。
- 查看明细入口。

明细表必须支持：

- 排序。
- 筛选。
- 字段设置。
- 行级下钻。
- 证据查看。
- 导出当前结果。

### 18.4 各主题的功能排版

#### 总览数据

```text
经营结论
  -> 销售 / 利润 / 流量 / 转化 / 推广五组指标
    -> 日趋势
      -> 异常指标和待处理事项
```

功能重点：

- 快速判断商品经营结果。
- 点击异常指标跳转到对应主题。
- 从异常指标直接创建问题和运营动作。

#### 流量来源

```text
来源结构摘要
  -> 来源占比和贡献图
    -> 来源明细表
      -> 来源商品/渠道下钻
```

功能重点：

- 按来源筛选。
- 按访客、支付、转化和 UV 价值排序。
- 查看来源变化。
- 从低转化来源创建诊断任务。

#### 搜索分析

```text
搜索结论
  -> 搜索访客、点击、成交、转化指标
    -> 关键词分组
      -> 关键词明细
```

关键词分组至少包括：

- 高流量低转化。
- 高转化低流量。
- 高花费低产出。
- 有展现无点击。
- 有点击无成交。

#### 标题优化

```text
当前标题与版本状态
  -> 词覆盖和搜索贡献
    -> 历史版本
      -> 变更动作与观察窗口
```

功能重点：

- 对比标题版本。
- 标记新增、删除和保留关键词。
- 记录修改人和修改时间。
- 将标题修改绑定到后续观察窗口。

#### 推广分析

```text
推广结论
  -> 投放核心指标
    -> 渠道分组
      -> 计划明细
        -> 单元/关键词/人群下钻
```

推荐固定列：

- 渠道。
- 计划。
- 状态。
- 展现、点击、CTR。
- 花费、CPC、CPM。
- 成交、订单、加购、收藏。
- ROI、直接 ROI、间接 ROI。
- 花费/订单、直接花费/订单、间接花费/订单。

功能重点：

- 渠道、计划、商品和关键词粒度切换。
- 计划状态筛选。
- 展开计划明细。
- 查看推广证据。
- 创建降费、停投、扩量或继续观察动作。

#### SKU、地域、时段分析

这三个主题采用相同排版，但只在数据真实可用时开放：

```text
结构结论
  -> 贡献排序
    -> 异常分组
      -> 明细与动作
```

### 18.5 抽屉、弹窗和操作反馈

使用场景必须区分：

| 组件 | 使用场景 |
| --- | --- |
| 侧边抽屉 | 规则说明、指标口径、数据证据、筛选详情 |
| 小弹窗 | 编辑负责人、标签、状态、日期等短操作 |
| 确认弹窗 | 批量操作、删除视窗、提交动作等不可逆操作 |
| 全屏工作区 | 字段配置、复杂导出、规则编辑、长明细 |

所有操作必须有明确结果：

- 成功：显示已保存、已创建或已导出。
- 失败：说明失败原因和重试入口。
- 部分成功：显示成功数量、失败数量和失败明细。
- 正在执行：显示进度或明确的处理中状态。

### 18.6 空态、异常态和数据质量排版

不能把所有异常都显示成同一个空白区域。页面必须区分：

```text
无数据：这个范围内没有记录
字段缺失：有记录，但无法计算当前指标
覆盖不完整：只有部分日期/商品/渠道有数据
来源不可用：数据源当前不可访问
计算失败：字段存在，但本次计算失败
```

表现要求：

- 卡片显示状态标签和不可计算数量。
- 指标显示状态原因，不能用 0 替代。
- 表格显示缺失字段提示和可用字段。
- 图表显示覆盖范围。
- 导出携带 availability、missing_fields 和 limitations。

### 18.7 响应式排版

#### 桌面端

- 以 1440px 左右宽度作为完整工作区设计基准。
- 商品列表允许横向滚动，但商品身份列和动作列固定。
- 规则卡片优先显示完整条件和变化值。
- 商品工作台允许主题内容使用宽表。

#### 平板端

- 上下文工具栏分两行。
- 卡片按两列排列。
- 指标行允许横向滚动。
- 明细表保持关键列，非关键字段进入字段设置。

#### 移动端

- 首屏只保留商品身份、核心结果、问题标签和主要动作。
- 规则卡片改为纵向列表。
- 商品表改为商品卡片，不强行压缩成十几列。
- 主题 Tab 可横向滑动。
- 趋势、明细和证据按折叠区展开。
- 批量运营和复杂字段配置提示使用桌面端完成，不在移动端伪造完整能力。

### 18.8 排版验收标准

- 用户进入商品总览后，3 秒内能看见当前店铺、时间范围、数据截止时间和主要问题集合。
- 用户不打开新页面，也能从规则卡片进入对应商品列表。
- 列表中能直接完成筛选、排序、跟进、待办和进入商品详情。
- 商品详情滚动时始终能识别当前商品和当前时间范围。
- 主题切换不会丢失商品、日期、对比方式和来源规则。
- 每个主题都能从结论进入证据，从证据进入动作。
- 桌面端不因字段增加导致商品身份列和操作列不可用。
- 移动端不出现横向页面整体溢出，宽表只在表格容器内部滚动。
- 空数据、缺字段、部分覆盖和计算失败在视觉上有明确区别。

## 19. 还需要补齐的产品级规范

排版和功能落位完成后，还不能直接进入大规模开发。边界 BI 这类页面的复刻质量，最终还取决于以下几层产品规范。

### 19.1 交互不是“能点击”，而是要有工作流

每个主要操作都要明确起点、过程、结果和返回路径：

| 操作 | 起点 | 过程 | 结果 | 返回 |
| --- | --- | --- | --- | --- |
| 卡片下钻 | 经营分群卡片 | 带入规则和时间条件 | 商品集合列表 | 返回卡片上下文 |
| 指标下钻 | 商品行指标 | 选择分析主题 | 对应诊断页面 | 返回商品行和筛选 |
| 创建待办 | 异常指标或问题集合 | 填负责人、目标、截止日 | 待办进入动作中心 | 回到原问题 |
| 保存视窗 | 当前筛选和字段 | 命名并选择默认范围 | 生成可复用视窗 | 继续当前查询 |
| 批量操作 | 多选商品 | 校验可操作范围 | 成功/失败明细 | 保留选中结果 |

必须支持：

- 浏览器前进和后退。
- 刷新后恢复上下文。
- 取消正在执行的查询。
- 请求失败后重试。
- 批量操作部分成功后的失败明细。
- 从抽屉关闭后回到原滚动位置。

### 19.2 状态机要覆盖经营动作

商品跟进和运营动作不能只用一个“已处理/未处理”字段，应至少使用：

```text
未处理
  -> 已分配
    -> 处理中
      -> 观察中
        -> 待复盘
          -> 已完成
```

另设：

```text
已忽略
已暂停
结果不可计算
动作失败
```

每次状态变化都要记录：

- 操作人。
- 操作时间。
- 原状态和新状态。
- 关联问题、商品和指标。
- 备注及附件。

这样商品详情里的“跟进状态”才不是一个装饰标签，而是可审计的运营流程。

### 19.3 权限与数据范围

页面排版必须提前考虑权限，否则上线后会出现“看得到但不能操作”的混乱：

- 店铺权限：用户可查看哪些店铺。
- 商品权限：用户可查看哪些商品集合。
- 指标权限：利润、成本和推广数据是否对用户开放。
- 操作权限：谁能分配负责人、改规则、导出和关闭动作。
- 字段权限：敏感字段可见但不可导出，或完全隐藏。
- 规则权限：预置规则可用，个人规则仅本人可见，团队规则由管理员维护。

前端隐藏按钮不能代替后端鉴权。接口必须返回字段和操作的授权状态，页面再决定显示、禁用或完全不展示。

### 19.4 查询性能与加载策略

这类页面通常同时包含规则卡片、表格、趋势和明细，不能每次切换都重新加载全部数据。

建议：

- 首屏优先加载上下文、规则卡片和商品列表摘要。
- 主题 Tab 采用按需加载。
- 卡片结果和列表结果使用同一查询快照或缓存键。
- 日期、规则、商品和视窗变化时取消过期请求。
- 大表格采用分页或虚拟滚动。
- 图表和明细分离加载。
- 导出使用后台任务，不阻塞页面。
- 对同一商品和同一周期的主题结果设置短时缓存。

性能验收建议：

- 商品总览首屏先显示结构和状态，再填充数据。
- 主要查询有明确的加载骨架。
- 连续切换主题不会出现旧数据覆盖新数据。
- 1000 个商品以上时筛选、排序和分页仍可用。
- 导出任务有进度、完成通知和失败原因。

### 19.5 组件行为规范

应建立一套可复用的 BI 组件，而不是每个页面单独实现：

- `ContextToolbar`：日期、店铺、对比、刷新。
- `AppliedFilters`：规则和筛选条件。
- `RuleCard`：规则、命中数、变化、下钻。
- `MetricCell`：数值、单位、对比、状态、口径入口。
- `AvailabilityBadge`：可用、部分、缺失、无数据、失败。
- `DataEvidenceDrawer`：公式、来源、覆盖、限制。
- `ProductTable`：冻结列、字段模板、批量操作。
- `AnalysisTab`：主题状态和按需加载。
- `ActionPanel`：待办、负责人、观察窗口。
- `ExportDialog`：当前查询、字段、证据和导出任务。

组件必须统一：

- loading、empty、error、partial 状态。
- 数字、百分比、金额和时间格式。
- 正负变化颜色和无障碍语义。
- tooltip、帮助入口和口径入口。
- 抽屉宽度、弹窗尺寸和移动端行为。

### 19.6 排版背后的视觉规则

不需要复制 BI 的品牌样式，但需要复制它的视觉判断逻辑：

- 红色表示需要处理的风险，不表示所有下降。
- 绿色表示正向结果，但利润增长和销售增长不能混用同一解释。
- 灰色表示无数据或不可计算，不能让用户误认为表现为零。
- 数字优先右对齐，名称和标签左对齐。
- 同一列保持单位和小数位一致。
- 变化值同时显示方向和百分比，必要时显示绝对变化。
- 高密度表格优先保证可比较性，不用过多装饰。
- 规则卡片的颜色表达问题类型，不能只凭严重程度排序。

### 19.7 埋点和使用效果

复刻之后要知道哪些能力真正被使用，否则无法判断页面是否有效：

- 哪张规则卡片被点击最多。
- 卡片到列表的下钻率。
- 列表到商品详情的进入率。
- 哪些主题 Tab 被使用。
- 哪些指标被展开查看证据。
- 待办和运营动作的创建率。
- 动作完成后的复盘率。
- 用户在哪一步退出。
- 查询失败、导出失败和数据不可用次数。

这些数据用于优化页面顺序、默认字段和规则卡片，而不是只用于统计访问量。

### 19.8 版本、快照和可复现性

同一个日期范围内，如果规则、成本字段或数据源发生变化，结果可能不同。因此必须保存：

- 规则版本。
- 指标定义版本。
- 数据快照时间。
- 数据源版本或导入批次。
- 页面视窗版本。
- 导出时的查询条件和字段定义。

用户打开历史问题或历史导出时，应能看到当时使用的口径，而不是自动套用最新规则。

### 19.9 分阶段交付方式

建议按可用工作流交付，而不是按页面数量交付：

**第一批：发现问题**

- 商品总览。
- 规则卡片。
- 商品集合下钻。
- 商品列表筛选和排序。

**第二批：定位问题**

- 商品工作台总览。
- 流量来源。
- 搜索分析。
- 推广分析。

**第三批：推动动作**

- 跟进、负责人、待办。
- 观察窗口。
- 动作前后对比。
- 复盘结果。

**第四批：增强分析**

- 标题版本。
- SKU。
- 地域。
- 时段。
- 规则配置和历史快照。

每一批都必须能独立完成一条真实任务，不能出现页面完成了但用户无法从发现走到动作的情况。

### 19.10 最容易被忽略的验收问题

最终验收时还要专门检查：

- 同一商品因不同规则命中多次时，列表是否正确展示多标签。
- 规则卡片的占比在有效商品数变化后是否同步变化。
- 指标分母为零、退款大于销售、花费为零时是否有正确状态。
- 商品标题过长、商品无主图、商品已下架时是否仍能操作。
- 同一商品被多人同时跟进时是否有冲突提示。
- 用户切换店铺后是否清理了不属于新店铺的商品和规则状态。
- 导出字段是否与页面字段一致，是否带出口径和数据状态。
- 主题 Tab 快速连续切换时，旧请求是否会覆盖新结果。
- 权限变化后，已打开页面是否重新校验。

这些内容决定复刻的是一个真正可用的经营工作台，还是一个看起来像 BI 的静态界面。

## 20. 反向工程探测清单

在正式开发前，应把每个 BI 页面拆成“可观察事实”和“待确认推断”。不能只记录页面上看得到的文字和模块，还要记录每个交互改变了什么。

### 20.1 页面探测记录

每个页面至少建立一份页面档案：

```text
页面名称
页面 URL 和参数
进入条件
默认店铺
默认时间范围
默认对比方式
默认视图
首屏模块顺序
页面滚动方式
固定区域
页面级操作
模块级操作
数据加载时机
异常状态
离开页面时保存的状态
```

需要逐项探测：

- 首次进入页面默认选中了什么。
- 修改一个筛选条件后哪些模块刷新。
- 修改日期后哪些模块不刷新。
- 切换 Tab 是否重新请求数据。
- 关闭抽屉后是否保留滚动位置。
- 返回上一页后筛选、分页和排序是否恢复。
- 刷新页面后 URL 是否可以恢复完整状态。
- 页面是否存在隐藏的二级菜单、更多字段或右键能力。

### 20.2 功能探测记录

每个按钮和可点击区域都要记录：

| 探测项 | 需要确认的内容 |
| --- | --- |
| 点击对象 | 卡片、数字、标签、表头、行、图例还是按钮 |
| 触发结果 | 页面跳转、抽屉、弹窗、筛选变化还是下载 |
| 参数传递 | 商品、规则、日期、排序、字段和来源是否保留 |
| 数据变化 | 哪个区域刷新，是否出现旧数据残留 |
| 可逆性 | 是否可取消、返回、撤销或重试 |
| 权限表现 | 隐藏、禁用、提示无权限还是接口报错 |
| 空态表现 | 无数据、缺字段、权限不足是否区分 |

特别关注这些容易被忽略的能力：

- 卡片点击标题和点击数量是否有不同结果。
- 表头点击是否支持多级排序。
- 指标是否可以点击查看定义或明细。
- 标签是否可以反向筛选商品。
- 图表数据点是否可以下钻。
- 表格是否支持复制、固定列、调整列宽和导出。
- “更多数据”是否只是增加字段，还是改变数据粒度。
- 视图切换是否真正改变业务任务。

### 20.3 字段与指标探测

每个页面出现的字段建立字段字典，不以页面显示名称作为唯一标识：

```text
field_key
页面名称
显示名称
字段类型
单位
数据粒度
默认聚合
是否可排序
是否可筛选
是否可导出
是否可下钻
公式
依赖字段
来源
缺失表现
```

必须区分：

- 页面直接展示字段。
- 页面计算字段。
- 页面标签字段。
- 页面规则字段。
- 仅用于解释的证据字段。
- 仅用于后端排序但不展示的字段。

例如“利润”不能只记录为一个数字，还要确认它是实际导入字段、系统推导字段，还是 BI 内部成本模型的结果。

### 20.4 数据粒度探测

所有模块都要明确事实粒度，否则会出现重复汇总：

```text
店铺 × 日期
商品 × 日期
商品 × 来源 × 日期
商品 × 计划 × 日期
商品 × 关键词 × 日期
商品 × SKU × 日期
商品 × 地域 × 日期
商品 × 小时
```

需要实际验证：

- 同一商品在不同渠道的成交是否可以直接相加。
- 计划明细和商品经营结果是否来自同一归因口径。
- 加购、收藏、支付买家是否允许跨层级求和。
- 退款发生在何时，按支付日还是退款日归属。
- 跨天订单、跨月退款如何处理。
- 商品改名、换主图、下架后历史数据是否仍使用同一商品 ID。

### 20.5 对比与变化探测

页面上的“环比、同比、增长、下降”必须逐个确认：

- 对比周期是否等长。
- 周期不足时是否补齐空白日期。
- 当前周期数据不完整时是否允许比较。
- 变化值是绝对变化还是相对变化。
- 分母为零时如何展示。
- 当前值和对比值分别使用什么数据快照。
- 跨月、跨年和自然周如何处理。

不能看到“增长 20%”就默认使用：

```text
(当前值 - 对比值) / 对比值
```

还要确认 BI 是否采用有效天数、商品集合、支付日期或其他分母。

### 20.6 业务口径验证

对每个关键指标建立“页面观察值、接口返回值、项目计算值”三方比对：

```text
BI 页面显示值
  ↔ BI 可见数据或导出值
    ↔ 本项目计算结果
```

验证对象至少包括：

- 销售额。
- 退款额和退款率。
- 推广花费。
- 推广占比。
- 利润和利润率。
- 访客和支付转化率。
- 客单价。
- ROI。
- 直接成交和间接成交。
- 加购、收藏及其转化。

每个差异都要归类为：

```text
字段不同
时间不同
粒度不同
归因不同
过滤条件不同
四舍五入不同
数据延迟不同
真实口径未知
```

### 20.7 证据等级

规划和开发任务中应给结论标注证据等级：

| 等级 | 含义 | 使用方式 |
| --- | --- | --- |
| A | 页面和可见数据均已验证 | 可直接进入实现 |
| B | 页面行为已验证，底层口径待确认 | 可做交互原型，暂缓固化公式 |
| C | 根据页面结构推断 | 只能进入待确认清单 |
| D | 仅凭行业经验假设 | 不得作为复刻事实 |

这样可以防止把“看起来应该有”的能力误写成“BI 已经验证的能力”。

## 21. 开发前必须冻结的决策

正式写代码前，以下决策必须明确，否则后续会反复返工：

1. 商品唯一标识使用商品 ID、链接 ID 还是店铺内商品编码。
2. 时间范围使用自然日、自然周、自然月还是数据有效日。
3. 利润、成本和退款采用哪套正式口径。
4. 推广数据按哪个归因粒度接入商品工作台。
5. 规则卡片是实时计算还是保存周期快照。
6. 商品集合下钻是否允许多个规则同时叠加。
7. 个人视窗和团队视窗的权限边界。
8. 导出是否包含隐藏字段、证据字段和数据质量字段。
9. 历史问题是否必须按照历史规则版本重放。
10. 移动端是完整操作端还是只做查看和快速处理。

如果这些决策没有冻结，页面即使完成，指标、列表和详情也可能互相不一致。

## 22. 最终探测产物

正式开发前，建议形成以下可审计产物：

- 页面清单。
- 页面截图和关键状态截图。
- 页面交互录屏或操作步骤。
- URL 参数字典。
- 字段字典。
- 指标口径表。
- 规则注册表草案。
- 数据粒度矩阵。
- 页面状态矩阵。
- 权限矩阵。
- API 请求和响应样例。
- BI 与本项目的指标差异表。
- A/B/C/D 证据等级清单。
- 未确认问题清单。

最终不是得到一张“页面复刻图”，而是得到一套可追溯的：

```text
页面行为
  + 数据字段
  + 指标口径
  + 规则条件
  + 交互状态
  + 权限边界
  + 证据等级
  = 可实施的 BI 能力规格
```
