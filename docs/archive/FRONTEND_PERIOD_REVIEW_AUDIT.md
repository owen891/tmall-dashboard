# /period-review 前端整改审查

审查日期：2026-09-21
审查范围：/period-review 当前运行页面、前端页面结构/交互脚本/样式、复盘上下文与动作接口协议。

## 3. 仍存在的缺口与风险

### P1：诊断弹窗没有消费后端完整证据，原因线索链不完整

现状：

后端已经返回 anomaly_tags、system_facts、unknowns，但弹窗只读取 row.anomaly_tags，系统依据使用前端固定文案，未展示 row.system_facts 和 row.unknowns。frontend/ui_demo/assets/period-review-live.js:233-260；services/period_review_service.py:889-948

影响：

用户看到的是“流量下降 / 客单价下降 / 投放效率下降 / 退款率上升”等结论，却不能在同一处看到触发该标签的当前值、对比值、数据完整性和未知项。这样无法可靠地从“异常”走到“原因线索”，容易把方向性指标误认为已确认原因。

整改建议：

1. 弹窗增加“事实证据”和“待补充数据”两个明确区块，逐条展示后端 system_facts、unknowns。
2. 每个异常标签旁边显示触发指标、当前值、对比值和变化比例。
3. 将“系统判断”改为“系统线索”，明确区分事实、推断和人工确认。

### P1：异常标签只有方向判断，没有阈值、显著性或证据等级

现状：

后端只要当前值低于上期值，便追加“流量下降 / 转化下降 / 客单价下降”等标签；投放效率和退款率同样采用简单方向比较。services/period_review_service.py:889-908

影响：

很小的波动也可能被标成异常。运行页实测某销售 TOP 商品同时显示多个风险标签，但弹窗没有说明下降幅度是否达到异常阈值，也没有说明数据覆盖是否完整。诊断结果因此更像“变化提示”，还不是可直接驱动动作的异常判定。

整改建议：

1. 为标签增加最小绝对变化和相对变化阈值，阈值按指标分别配置。
2. 展示“轻微变化 / 重点异常 / 数据不足”三个证据等级。
3. 只有达到阈值的标签才进入“建议动作”区域，其他变化保留为普通事实。

### P1：动作字段与异常类型没有真正绑定，目标指标被固定为支付金额

现状：

无论商品是流量、转化、投放或退款异常，表单都固定提交 purpose_type: increase_sales 和 target_metric: payment_amount。frontend/ui_demo/assets/period-review-live.js:280-294

影响：

动作可以被创建，但无法表达“提升访客”“恢复转化”“降低退款率”“改善投放 ROI”等不同验收目标。后续观察重算只能围绕支付金额，不足以验证原因对应的动作是否有效。

整改建议：

1. 根据异常标签预选动作目标，但允许人工调整。
2. 目标指标至少支持 payment_amount、visitors、conversion、aov、ad_roi、refund_rate。
3. 创建动作时保存触发标签、基线值、目标值和验收口径，后续复盘按同一指标回流。

### P1：动作创建表单允许创建“没有验收标准”的动作

现状：

“动作详情”是必填，但默认为空；表单没有目标值、验收条件或动作前基线字段。frontend/ui_demo/assets/period-review-live.js:261-275

影响：

用户可以输入一段泛化描述后创建动作，造成“已创建”但不可验收，违背整改目标中的“沉淀可验收的下一步动作”。

整改建议：

动作表单最少增加：动作前事实、具体处理、目标指标、目标值/阈值、验收日期、验收人。提交前检查目标值和验收条件不能只依赖自由文本。

### P1：执行跟踪缺少页面侧的阻塞和异常处理入口

现状：

页面根据状态提供推进按钮，但 renderActionList 没有“标记阻塞”、填写阻塞原因/预计恢复时间、取消动作或编辑负责人/截止日期的入口。frontend/ui_demo/assets/period-review-live.js:599-618。后端状态机虽然支持 blocked，并要求阻塞原因和恢复日期。services/actions_service.py:20-30,115-140

影响：

动作一旦无法执行，页面只能继续显示在待处理列表，无法把“卡点 -> 资源需求 -> 恢复时间”沉淀到复盘中；“阻塞与待处理”分组存在，但用户缺少把动作送入该分组的操作。

整改建议：

增加动作行菜单或详情弹窗，支持：标记阻塞、填写阻塞原因、预计恢复日期、重新进入执行、取消动作、修改负责人和计划日期。阻塞状态提交成功后应立即刷新驾驶舱计数和复盘素材。

### P2：货品表只展示排名和数值，没有在扫描层呈现异常标签

现状：

表格列只有商品、金额/变化、诊断按钮，没有标签或风险列。frontend/ui_demo/assets/period-review-live.js:574-605

影响：

用户必须逐条打开弹窗才能知道异常是流量、转化、客单、投放还是退款，无法快速筛选最值得先处理的商品。

整改建议：

在下滑榜增加“异常线索”列，最多展示 2 至 3 个高优先级标签，并保留弹窗查看完整证据；增加按异常类型筛选或排序。

### P2：动作列表信息密度不足，执行人员无法快速判断责任和验收进度

现状：

动作行主要显示商品、动作类型、状态、计划日期、执行日期和目的说明。frontend/ui_demo/assets/period-review-live.js:599-618

影响：

负责人、观察窗口、目标指标、观察前后值和待复盘原因没有作为常驻信息显示；执行列表更像状态日志，不能作为日常跟进清单。

整改建议：

动作行至少展示负责人、计划/执行/验收日期、目标指标、观察窗口、当前结果和下一步；详情弹窗展示完整历史。

### P2：周/月切换与顶栏统计时间存在可见口径不一致

现状：

运行页实测顶栏统计时间为 2026-08-21 ~ 2026-09-19，但当前周复盘显示 2026年第38周（09-14 ~ 09-20）。页面说明复盘周期按结束日期识别自然周，逻辑上可以成立，但用户会看到当前复盘结束日超出顶栏范围 1 天。前端周期计算和切换逻辑见 frontend/ui_demo/assets/period-review-live.js:144-161,1141-1153。

影响：

用户可能误以为复盘数据超出了当前筛选范围，周/月切换后的数据边界不够直观。

整改建议：

1. 顶栏切换到“本周/上周”时，显式把结束日对齐到周日并展示覆盖范围。
2. 或在复盘页面把“统计时间”和“复盘周期”拆成两个有明确关系的控件，避免一个控件驱动另一个控件却只在说明文字中解释。
3. 周/月切换验收时同时核对周期 key、开始/结束日期、对比周期 key、商品榜和 KPI 是否全部更新。

### P2：表格没有独立的横向滚动容器，长商品标题可能挤压操作列

现状：

商品标题很长，运行页实际商品名达到几十字；表格本身为 width: 100%，样式未给表格外层增加横向滚动或固定操作列。frontend/ui_demo/assets/period-review.css:349-378。

影响：

在窄桌面或移动宽度下，金额列和“查看诊断”操作列可能被挤压，扫描效率下降。

整改建议：

给商品表增加可横向滚动的容器，商品列设置最小宽度，诊断列固定在右侧；长标题使用两行截断并提供完整标题的可访问文本。

### P2：当前测试没有覆盖关键前端闭环

现状：

当前已验证 node --check、前端运行时检查及 tests/test_period_reviews_api.py（15 passed, 5 subtests passed）。这些检查能证明脚本可解析、API 聚合正确，但没有覆盖浏览器中的月度切换、打开诊断、提交动作、状态推进、阻塞和提交验收。

影响：

核心链路的成功标准仍依赖人工观察，后续改动容易出现“接口通过但页面断链”。

整改建议：

补充一条低门禁的浏览器冒烟流程，覆盖主链路即可，不需要扩大到全站 UI 回归。

## 4. 建议实施顺序

### 第一批：先让诊断可信

1. 在弹窗真实呈现 system_facts、unknowns、触发指标和变化值。
2. 给异常标签补证据等级和阈值说明。
3. 下滑榜增加异常线索列，减少逐条打开弹窗的成本。

### 第二批：让动作可验收

1. 根据异常类型绑定目标指标和动作目的。
2. 增加目标值、验收标准、负责人、验收日期。
3. 保存触发异常、基线值和目标口径，作为后续观察的固定基线。

### 第三批：补齐执行跟踪

1. 增加阻塞、取消、编辑和重新执行入口。
2. 动作列表显示责任、期限、观察窗口和结果。
3. 在“待复盘”动作中完成验收后，将结论和下一步回流到周/月复盘。

### 第四批：降低回归风险

用一条浏览器冒烟覆盖：周复盘加载 -> 月复盘切换 -> 下滑商品 -> 诊断弹窗 -> 创建动作 -> 动作进入列表 -> 状态推进 -> 观察重算 -> 提交验收。只对核心链路加门禁，不扩大全量页面测试。

## 5. 建议验收步骤

### A. 周/月切换

1. 打开 http://127.0.0.1:5178/period-review，确认默认周周期显示周期 key、开始/结束日期和对比周期。
2. 点击“月复盘”，确认页面显示月周期 key（例如 2026-09），KPI、销售榜、下滑榜、动作列表随月周期重新加载。
3. 切回“周复盘”，确认恢复 2026-W38，不会残留月度自定义对比值。
4. 分别选择环比、同比、自定义、不对比，确认对比周期和下滑榜排序同步变化；缺数据时显示“不可判断/待补充”，不显示为 0。

### B. 异常商品到原因线索

1. 进入“货品与异常”，确认销售贡献 TOP10 和下滑 TOP10 的数量、排序和当前周期一致。
2. 在下滑榜打开商品诊断，确认商品 ID、当前/基线 GSV、变化比例、访客、转化、客单、推广、退款均有值或明确缺失原因。
3. 逐条核对每个异常标签都能对应事实指标、当前值、对比值和证据等级。
4. 对缺少基线的数据验证显示“不可判断/待补充”，不能因为 SQL 聚合缺行而显示为 0。

### C. 创建动作

1. 从下滑商品诊断弹窗创建动作，确认商品 ID、来源周期、品类口径自动带入。
2. 填写动作详情、目标指标、目标值、负责人、计划日期、观察窗口和验收标准。
3. 提交后确认 POST /api/actions 成功，弹窗关闭，动作出现在“动作与计划”。
4. 刷新页面或重新选择相同周期，确认动作仍存在，且没有重复创建。

### D. 执行跟踪与下期验证

1. 将动作从草稿推进到待执行、执行中、观察中，确认每次状态变化后列表分组和驾驶舱计数更新。
2. 标记阻塞并填写阻塞原因、预计恢复日期，确认动作进入“阻塞与待处理”。
3. 观察窗口数据完整时执行重算，确认显示执行前、执行后、变化值和计算说明。
4. 提交复盘验收，填写有效性、原因、结论、下一步和复盘人。
5. 切换到下一周/下一月，确认上一期动作结果可作为“上期做了什么”和下一期计划的可追溯证据。
