# TM Dashboard 数据能力底稿

> 版本：0.1
> 盘点时间：2026-08-15
> 数据库：`data/dashboard.db`
> 数据最新日期：2026-08-12
> 用途：先确认可获得的数据，再决定指标、业务能力和产品页面。

## 1. 结论摘要

当前项目不是“没有数据”，而是数据分布在不同粒度，覆盖率不一致。产品能力必须按商品、日期和数据域分别判断，不能用一个全局的“有数据/没数据”控制整页。

当前最适合优先产品化的能力：

1. 店铺经营总览：店铺日事实完整，适合做趋势和核心经营指标。
2. 商品经营分析：商品日/月事实可支持排行、趋势、转化和广告表现，但商品覆盖不完整。
3. 推广效果分析：推广日事实可支持渠道和商品维度的花费、归因成交、ROI 分析。
4. 生命周期评估：可以由商品日/月数据派生，结果应标记证据天数、完整月份和置信度。
5. 数据中心：导入预览、质量校验、批次审计和冲突安全撤销。

当前不应直接承诺：利润、库存周转、用户 cohort、严格因果归因、完整市场机会分析。

## 3. 粒度和数据边界

所有指标必须先确认粒度，再确认聚合方式。

| 粒度 | 唯一业务键 | 可以直接做什么 | 不能直接做什么 |
|---|---|---|---|
| `shop_day` | `shop_id + date` | 店铺趋势、净销售额、退款率、店铺转化 | 商品排行、单品归因 |
| `product_day` | `product_id + date` | 商品趋势、商品转化、商品广告依赖 | 用户留存、订单级复购 |
| `product_week` | `product_id + week_start` | 周期比较、周复盘 | 日级异常解释 |
| `product_month` | `product_id + month` | 月度趋势、生命周期、季节性 | 精确日级动作归因 |
| `ad_product_day` | `date + channel + product_id` | 渠道/商品推广表现 | 严格因果归因 |
| `review` | `product_id + review_date + id` | 评价文本、情绪、问题维度 | 全量用户满意度 |
| `lifecycle_assessment` | `product_id + assessment_date` | 阶段推荐、证据、人工锁定 | 原始销售事实 |

## 4. 字段质量和风险

### 4.1 已确认可用

- `products.product_id`、`products.title` 完整。
- `store_daily_facts` 的 589 个日期均有核心金额、访客和买家字段。
- `daily_data` 和 `monthly_data` 的核心商品、日期、支付金额字段当前没有空值。
- `promotion_daily_facts` 的日期、渠道、商品、花费和归因成交字段当前完整。

### 4.2 覆盖不足但可以做部分能力

- 商品日事实仅覆盖 882 / 1,847 个商品，约 48%。商品列表和商品经营分析必须区分“无商品事实”和“指标为 0”。
- 商品月事实覆盖 1,711 / 1,847 个商品，约 93%，但生命周期的季节性仍需检查每月是否有完整日覆盖。
- 评价只有 32 条，不能从中推导全店客服质量或总体满意度。
- 推广事实只覆盖 8 个商品，不能代表全商品推广表现。

### 4.3 当前明显不应直接使用的字段

- `products.product_growth_stage` 当前全部为空，不能直接作为生命周期结果。
- `monthly_data.industry_ctr` 当前全部为 0，不能作为行业基准。
- `market_analysis` 和 `market_keyword_opportunities` 当前为空，市场机会页面只能显示未接入状态。

### 4.4 数据批次风险

当前 `import_batches` 同时存在 demo 批次和真实导入批次。真实库和演示库必须隔离；演示数据只能写入 `data/demo/dashboard.db`。

## 5. 指标能力目录

指标统一使用 `sum_then_derive`：先汇总依赖字段，再计算比例或单价，不允许平均行比例。

| 指标 | 公式 | 最小依赖 | 当前能力 |
|---|---|---|---|
| 净销售额 | `sum(payment_amount) - sum(successful_refund_amount)` | 支付金额、成功退款金额 | 店铺日、商品日/月可用 |
| 退款率 | `sum(refund) / sum(payment)` | 退款金额、支付金额 | 店铺日、商品日/月可用 |
| 支付转化率 | `sum(payment_buyers) / sum(product_visitors)` | 支付买家、商品访客 | 店铺日、商品日/月可用 |
| 客单价 | `sum(payment_amount) / sum(payment_buyers)` | 支付金额、支付买家 | 店铺日、商品日/月可用 |
| 费用率 | `sum(ad_spend) / sum(payment_amount)` | 广告花费、支付金额 | 店铺日、商品日可用 |
| 广告 ROI | `sum(attributed_payment_amount) / sum(ad_spend)` | 归因成交、广告花费 | 推广日可用 |
| 老客占比 | `sum(returning_payment_buyers) / sum(payment_buyers)` | 老客买家、支付买家 | 店铺日可用，商品层需谨慎 |
| 增长率 | 当前窗口值 / 对比窗口值 - 1 | 同一粒度的两个时间窗口 | 商品、店铺可用 |
| 推广依赖度 | `sum(ad_spend) / sum(payment_amount)` | 商品/店铺花费、支付金额 | 商品日可用 |

## 6. 生命周期能力方案

### 6.1 计算输入

生命周期不是导入字段，而是由以下事实派生：

- 商品主数据：`product_id`、`title`、`list_date`、`status`。
- 商品日事实：日期、支付金额、访客、买家、转化率、广告花费。
- 商品月事实：月份、支付金额和完整日覆盖。

### 6.2 阶段规则

| 阶段 | 推导规则 | 证据要求 |
|---|---|---|
| 数据积累中 | 连续有效日少于 60 天 | 只显示积累状态，不输出确定阶段 |
| 新品 | 前 30 天成交为 0，最近 30 天有成交 | 至少 60 个连续有效日 |
| 爆发 | 最近 30 天成交不低于前 30 天的 160% | 至少 60 个连续有效日 |
| 成长 | 最近 30 天成交不低于前 30 天的 125% | 至少 60 个连续有效日 |
| 成熟 | 不满足增长或下降阈值 | 至少 60 个连续有效日 |
| 衰退 | 最近 30 天成交不高于前 30 天的 65% | 至少 60 个连续有效日 |
| 清仓候选 | 低成交、低转化、持续下降，并结合商品状态/库存策略 | 当前字段不足以自动确认清仓 |

### 6.3 季节性规则

只有至少 12 个完整月份才允许输出产品级季节性。完整月份需要日事实覆盖该月预期天数；不足时返回“季节性证据不足”。

### 6.4 生命周期返回契约

每个商品都应独立返回：

```json
{
  "stage": "growth",
  "recommended_stage": "growth",
  "confidence": "medium",
  "continuous_valid_days": 128,
  "complete_months": 6,
  "data_cutoff_date": "2026-08-12",
  "rationale": "最近30天支付金额较前30天增长...",
  "source": "derived",
  "algorithm_version": "lifecycle-v1"
}
```

页面整体状态应支持 `partial`：有数据的商品正常展示，数据不足的商品显示原因，不能因为少数商品不足而屏蔽整页。

## 7. 能力分级

| 等级 | 含义 | 产品行为 |
|---|---|---|
| A 可用 | 依赖字段齐全，覆盖满足当前窗口 | 正常展示、筛选、导出 |
| B 部分可用 | 只有部分商品、日期或粒度满足要求 | 展示可用部分，并显示覆盖范围 |
| C 演示可用 | 真实源数据不足，使用独立 demo 数据验证流程 | 必须标注“演示数据” |
| D 不支持 | 缺少必要事实，不能可靠推导 | 隐藏或禁用操作，说明缺口 |

当前建议：

- A：店铺日总览、商品基础目录、核心交易指标、推广 ROI、导入审计。
- B：商品经营排行、商品详情、生命周期、商品问题提醒、评价分析。
- C：完整生命周期阶段分布、季节性示例、运营动作闭环演示。
- D：利润、库存周转、用户 cohort、严格因果归因、完整市场机会。

## 8. 问题提醒能力

不引入“商品健康分”或综合评分。产品只输出可解释、可执行的问题提醒，每条提醒必须保留原始证据。

### 8.1 提醒结构

```text
商品
→ 问题类型
→ 指标和时间窗口
→ 当前值 / 对比值 / 变化幅度
→ 证据完整性
→ 建议动作
```

示例问题类型：

| 问题类型 | 触发条件示例 | 建议动作 |
|---|---|---|
| 销售下降 | 最近 30 天支付金额较前 30 天下降超过阈值 | 检查流量、价格和活动 |
| 转化偏低 | 访客稳定但支付转化率持续低于基线 | 检查主图、详情页和价格 |
| 推广低效 | 广告花费增加但归因成交或 ROI 下降 | 降低低效渠道预算 |
| 退款上升 | 退款率超过商品自身历史基线 | 检查质量、描述和履约 |
| 流量异常 | 搜索、推荐或付费访客突然下降 | 检查渠道和投放状态 |
| 数据缺口 | 连续有效日不足或日期存在缺口 | 补充数据，不输出确定结论 |

提醒列表必须支持按问题类型、严重程度、商品、日期和来源批次筛选；提醒详情必须能回到对应事实数据。

### 8.2 与生命周期的关系

生命周期是阶段判断，问题提醒是异常事实，两者分开保存：

- 生命周期回答“商品处于什么阶段”。
- 问题提醒回答“当前具体哪里有问题”。
- 一个成熟商品可以同时有“退款上升”提醒。
- 一个成长商品也可能有“推广低效”提醒。

## 9. 产品化顺序

### P0：先交付真实数据能支撑的能力

1. 店铺经营总览。
2. 商品经营列表和详情。
3. 推广渠道/商品分析。
4. 数据中心导入和质量报告。

### P1：基于派生能力扩展

1. 商品生命周期评估。
2. 商品问题提醒和异常清单。
3. 运营动作、观察窗口和复盘。
4. 周/月周期复盘。

### P2：补齐数据源后再开放

1. 市场关键词和机会分析。
2. 库存与利润。
3. 用户 cohort 和复购留存。
4. 严格因果归因。

## 9. 演示数据补齐规范

演示数据必须满足：

1. 写入独立数据库，不修改 `data/dashboard.db`。
2. 原始事实先生成，生命周期结果由同一套算法计算。
3. 每个 demo 商品代表一种走势，而不是只写一个阶段枚举。
4. 所有演示记录带 `DEMO-` 标识或 `demo-seed` 来源。
5. 页面和 API 显示数据来源、截止日期和算法版本。
6. 演示库可以覆盖新品、成长、爆发、成熟、衰退、季节性和数据不足七种场景。

## 10. 验收门槛

数据能力进入正式页面前，至少满足：

- 有明确的表、粒度、唯一键和时间范围。
- 核心字段空值率和覆盖率可查询。
- 指标公式在代码和文档中只有一个定义。
- 数据不足时返回 `availability` 和 `missing_inputs`，不补零伪造结果。
- 派生结果包含证据范围、截止日期、置信度和理由。
- 演示数据和真实数据物理隔离。
- API、前端能力门控和测试使用同一套能力名称。
- 页面可以表达“部分可用”，而不是只有成功/失败两种状态。

## 11. 当前底稿的主要缺口

1. 需要把商品日/月事实的覆盖率、连续有效日和完整月份统计做成接口，而不是只在后台脚本里计算。
2. 需要将生命周期结果标记为 `derived` 或 `manual`，区分系统推导和人工锁定。
3. 需要把 demo seed 从“直接写生命周期结果”改成“生成事实后调用算法”。
4. 需要修正生命周期 API 的全量 `all(...)` 判断，改为逐商品状态和整体 `partial` 状态。
5. 需要清理真实库中的 demo 批次，发布前通过严格审计。
