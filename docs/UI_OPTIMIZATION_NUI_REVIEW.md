# Tmall Dashboard UI 收敛方案 — NUI 审查意见

> 审查日期：2026-10-01  
> 审查对象：`E:\www\tmall-dashboard\docs\UI_OPTIMIZATION_IMPLEMENTATION_PLAN.md`  
> 审查方式：按 NUI 的产品含义、证据表达、组件边界、交互一致性和工程验收原则进行审查

## 1. 结论

现有方案方向是正确的，尤其是：

- 不迁移 React/Vue；
- 先统一页面结构，再迁移页面；
- 先改数据概览、复盘、商品、推广、数据中心；
- 用少数公共组件解决重复实现；
- 不继续堆叠视觉装饰。

但当前方案更像“改造方向清单”，还不是可以直接执行的 NUI 页面实施方案。

需要补充的不是更多组件，而是每个页面的：

```text
用户对象
→ 当前决策
→ 需要的证据
→ 可执行动作
→ 数据状态
→ 响应式约束
→ 验收方式
```

### 总体判断

```text
方向正确：约 70%
实施约束不足：约 30%
```

主要缺口集中在：页面契约、数据语义、图表表达、响应式验收、可访问性和页面级回归验证。

---

## 2. 与 NUI 原则一致的部分

### 2.1 页面收敛方向正确

方案把页面收敛为：

- 看板型；
- 列表型；
- 诊断型；
- 配置型；
- 复盘型。

这符合 NUI 的“先根据用户任务选择页面结构，而不是先堆组件”的原则。

### 2.2 首屏顺序正确

方案提出：

```text
先看结论
→ 再看指标
→ 再看异常或证据
→ 最后执行操作
```

这是当前项目最需要的改进，也符合 NUI 的三层设计方法：

```text
产品含义 → 证据 → 表达
```

### 2.3 技术边界正确

继续使用原生 JavaScript 是合理的。NUI 不要求迁移 React 或 Vue，当前项目可以把 NUI 用作：

- 信息架构规范；
- 设计 token 规范；
- 表格、筛选、抽屉交互规范；
- AntV 数据表达原则；
- 页面审查和回归标准。

不需要引入 Ant Design 依赖，只借用其成熟的交互习惯。

### 2.4 不做全量重构是正确的

当前工作区存在大量业务 WIP，因此按“公共组件 → 五个重点页面 → 剩余页面 → 清理”的顺序是合理的。

## 3. 必须修正的部分

## 3.1 “一个页面只有一个主要操作”需要改写

原方案写的是：

```text
每个页面最多一个主要操作
```

这个规则过于死板。NUI 要求的是“一个主要决策区”，而不是任何页面只能有一个动作。

建议改为：

```text
每个页面只有一个主要决策区；
决策区内允许一个主动作，其他动作降级为次要动作；
不删除原有能力，只降低次要能力的视觉权重。
```

例如商品列表页的主决策是“找出需要处理的商品”，主动作可以是“查看详情”，但搜索、筛选、导出、字段设置仍然必须保留。

---

## 3.2 “三类数据状态”不能覆盖真实数据语义

原方案希望 UI 只展示：

```text
加载中
暂无可用数据
加载失败
```

这个方向适合减少用户看到的术语，但不能在数据层把以下状态混为一谈：

```text
真实为 0
暂无记录
字段缺失
数据过期
部分数据可用
权限不足
请求失败
```

建议改成两层：

### 用户可见的主状态

```text
加载中
暂无可用数据
暂时无法加载
```

### 辅助原因

```text
当前筛选范围没有记录
数据仍在积累
缺少推广字段
数据更新时间超过 24 小时
部分指标暂不可用
没有访问权限
```

也就是说：

> UI 语言可以收敛，数据语义不能被压扁。

验收时仍需覆盖 zero、null、unavailable、stale、partial、permission、error 等场景。

---

## 3.3 每个页面需要补充“页面契约”

当前方案只有页面类型和页面结构，还缺少可执行的页面契约。

每个重点页面至少补充以下内容：

```text
页面名称：
主要对象：
用户任务：
主要决策：
主要动作：
必须保留的能力：
首屏证据：
数据来源和更新时间：
加载 / 空 / 零值 / 部分 / 失败状态：
桌面布局：
移动端布局：
验收方式：
```

建议第一批页面先建立五份契约：

```text
overview.page-contract.md
period-review.page-contract.md
products.page-contract.md
promotion.page-contract.md
data-center.page-contract.md
```

不需要立刻建立复杂文档体系，直接放在方案 MD 的附录即可。

---

## 3.4 缺少图表和指标的表达规则

方案提到“统一指标卡”和“统一数据可视化”，但还没有规定：

- 每个指标回答什么问题；
- 对比周期是什么；
- 单位是什么；
- 数据更新时间是什么；
- 数据来源是什么；
- 什么时候使用折线图、柱状图、表格或趋势摘要；
- 关键数字是否可以不依赖 hover 才能读到。

NUI/AntV 的要求不是“图表统一”，而是“图表服务于比较和行动”。

建议增加以下规则：

```text
每个指标必须有业务问题；
每个趋势必须有时间范围和对比对象；
每个金额、比例、数量必须有单位；
关键值必须有文字或表格补充；
颜色不能作为唯一的状态表达；
没有比较任务时，不使用装饰性图表。
```

例如：

```text
转化率 3.8%
较上周期 -0.6 个百分点
数据范围：近 30 天
更新时间：今天 09:30
```

而不是只展示一个大号 `3.8%`。

---

## 3.5 缺少设计 token 映射

原方案提出了颜色和间距统一，但还不够工程化。

应该把现有：

```text
E:\www\tmall-dashboard\frontend\ui_demo\assets\tokens.css
```

作为唯一 token 入口，公共组件不得散落硬编码颜色和间距。

建议按语义补齐：

```css
--color-canvas
--color-surface
--color-border
--color-text-primary
--color-text-secondary
--color-text-muted
--color-accent
--color-success
--color-warning
--color-danger
--radius-control
--radius-panel
--shadow-overlay
--space-page
--space-section
--space-control
```

不要求使用 NUI 默认的靛蓝色。当前项目应保留已有品牌主色，只把颜色命名改成语义角色。

---

## 3.6 响应式验收需要具体化

现有方案只写了“移动端不出现横向溢出和操作挤压”，还不够。

至少需要在以下宽度检查：

```text
390px
768px
1280px
1440px
```

重点检查：

- 页面头部是否折行；
- 上下文筛选是否换行或变成抽屉；
- 表格是否有明确横向滚动容器；
- 详情抽屉是否变成全屏面板；
- 固定底部操作栏是否遮挡内容；
- 长商品名、金额、百分比是否正确换行；
- 空状态是否仍然可读。

---

## 3.7 无障碍和键盘行为需要加入验收

原方案暂时没有覆盖：

- 键盘可达；
- 焦点状态；
- 抽屉打开后的焦点管理；
- Esc 关闭；
- 图标按钮的无障碍名称；
- 颜色对比度；
- 灰度下的信息可读性。

这些内容应加入统一验收标准，而不是等最后补救。

---

## 3.8 数据中心不宜直接套用“任务队列”

NUI 明确要求只有真实存在排队、分流、处理任务时才使用队列式布局。

当前数据中心建议保留：

```text
当前数据状态
最近更新时间
影响范围
建议操作
```

只有当系统确实存在多个待处理采集任务、任务状态和优先级时，才引入队列或任务列表。

## 5. 五个重点页面的 NUI 页面契约摘要

### 5.1 数据概览

```text
主要对象：店铺整体经营状态
用户任务：判断当前经营是否正常，并找到优先处理事项
主要决策：先处理增长机会还是经营风险
首屏证据：核心指标、周期变化、异常商品、数据更新时间
主动作：进入重点问题
布局：结论区 → 核心指标 → 异常区 → 重点对象 → 行动
```

不建议把所有图表都放在首屏。每个图表都要绑定一个具体问题。

### 5.2 周月复盘

```text
主要对象：一个复盘周期
用户任务：确认目标差距、找到原因、形成行动计划
主要决策：哪些问题需要进入行动计划
首屏证据：目标完成度、周期变化、主要差距、数据可信度
主动作：进入问题清单或生成行动项
布局：复盘范围 → 结论 → 问题 → 证据工作区 → 行动
```

### 5.3 商品

```text
主要对象：商品记录
用户任务：筛选需要关注的商品并查看原因
主要决策：哪个商品需要处理
首屏证据：销售、流量、转化、库存或推广状态
主动作：查看详情
布局：上下文 → 工具栏 → 表格 → 抽屉
```

### 5.4 推广

```text
主要对象：推广计划或推广单元
用户任务：发现异常投放并判断是否调整
主要决策：哪个计划需要优化或暂停
首屏证据：消耗、成交、ROI、点击率、转化率、趋势
主动作：查看异常计划
布局：总览 → 异常 → 计划表格 → 详情
```

### 5.5 数据中心

```text
主要对象：数据源和数据更新状态
用户任务：确认数据是否可用，并完成必要补采
主要决策：是否需要补采或修复数据源
首屏证据：更新时间、覆盖范围、缺失字段、影响页面
主动作：执行建议操作
布局：状态 → 影响 → 建议操作 → 详细配置
```

## 7. NUI 版最终验收标准

### 含义和层级

- 两秒内能看出页面对象、当前状态和下一步动作；
- 每个页面只有一个主要决策区；
- 每个指标和图表都对应一个业务问题；
- 不隐藏或删除原有能力；
- shell 和页面不重复放标题、时间筛选、刷新、导出。

### 数据

- 区分真实零值、无记录、不可用、过期、部分可用和失败；
- 金额、比例、数量都有单位；
- 有需要时展示来源和更新时间；
- 关键图表有文字摘要或表格路径；
- 不依赖 hover 才能获得关键结论。

### 视觉

- 使用语义 token，不散落硬编码颜色；
- 静态内容优先使用间距和结构，不依赖阴影；
- 页面在 390px、768px、1280px、1440px 正常显示；
- 长文本、长数字和空状态有明确处理方式；
- 灰度模式下仍然可读。

### 交互和可访问性

- 主要控件可键盘访问；
- 抽屉和弹窗有正确焦点管理；
- 图标按钮有可访问名称；
- 状态不只依靠颜色表达；
- 对比度达到项目目标；
- 加载、成功、警告、错误有反馈。

### 工程

- 现有路由、API、导出、计算和权限不被破坏；
- 有目标页面的原始测试和状态测试；
- 真实路由在桌面、紧凑和移动尺寸完成渲染检查；
- 控制台没有新增错误；
- 废弃结构被删除或隔离，不使用假分支隐藏旧模板。

## 8. 最终建议

原方案不需要推翻，建议按以下方式定稿：

```text
保留：页面模板、六个组件、小批次实施、原生 JS
补充：页面契约、数据语义、图表规则、token 映射、响应式和无障碍验收
收紧：一个主要决策区，而不是一个页面只能有一个动作
```

最终使用 NUI 的方式应是：

> 用 NUI 约束产品含义、证据和交互；用现有 JavaScript 落地；用少量 Apple Liquid Glass 原则处理浮层质感；不把项目改造成 AI 控制台，也不引入新的前端框架。
