# 多 agent 编排（主控 / 执行 / 审核）

**一条收敛链 + 一条独立审核泳道。并行度由「写域是否互斥」决定，不由任务数量决定。**

本 SKILL 是可执行压缩版；完整细则、模板与本仓库命令清单见常驻文档 `docs/AGENT_TEAM_PLAYBOOK.md`。

## 四阶段三门禁

| 阶段 | 谁 | 产出 | 门禁 |
|---|---|---|---|
| L0 讨论收敛 | 只有主控（可加 1 个只读「反方律师」） | `spec.md` | ★ 人确认 |
| L1 规划 | 主控主笔 + 1 个架构对抗者 | `docs/<TOPIC>_PLAN_YYYYMMDD.md` + 任务卡 | ★ 人确认 |
| L2 执行 | 2–5 个 writer，写域互斥 | 代码 + `reports/<id>.md` | — |
| L3 审核 | 独立 verifier，**未参与实现** | 审核报告（附复现命令与原始输出） | ★ 主控终局 |

L2/L3 是**同一条流水线**：某任务完成即进审核，不设全局屏障；任务间依赖用 `blocked_by` 表达。

## 硬规则

**L0 讨论**
- 不派 writer。讨论是需求收敛，不是可并行工作。
- 边聊边写 `spec.md`（活文档），不要聊完再倒一遍。
- 冻结信号只有一个：**每条验收标准都能写成「可执行命令 + 期望输出」**，写不出来就不算冻结。
- 必须写**非目标**（本仓库最大的返工风险是「顺手改了指标口径」）。

**L1 规划**
- **契约先行**：先冻结函数签名 / API schema / 文件边界，再开第二个 writer。
- **契约自检（冻结前必做）**：① 每条验收标准能否在该契约下**同时**成立？② 返回值类型能否装下要暴露的字段？③ 仓库里是否已有测试**固化了待修行为**（有就把该测试文件列入写域）？——三条都在实战里翻过车。
- **穷举性假设单独列出并标注「未经核验」**，交给对抗者首发攻击（「所有调用点已收口」这类结论多半是假的）。
- 每条任务带 `文件:行号`；没有行号的条目说明还没定位到实现层，**不开工**。
- 任务卡 = 一个自包含 prompt（fresh teammate 没有你的上下文）。

**L2 执行**
- 并行阈值：写域互斥 **且** 任务 > 30 分钟 → 并行；单文件小改 / 探索性任务 → 主控自己做。
- **探索阶段绝不并行**（结论互相覆盖），先收敛成审计文档再进实现。
- 配额硬上限：writer 2–5、verifier 1–2、架构对抗 1。加人前先问「它的写域和谁不重叠」。
- 执行前打 baseline commit/tag；每个 writer 一个分支；**合并冲突就是写域重叠的报警器**。
- 进度写 `.tmp/agent-reports/<id>.md`，首行 `status: running|done|blocked`。不要发消息问「做完了吗」。
- **每轮 `wait_agent` 后核对任务板差集**：`派发集合 − completed` 里若还有 `pending`/`in_progress` 而 owner 已 inactive，说明任务被落下或卡住，主动催办——**不要等 writer 自报**。

**L3 审核**
- 审核者必须**能执行**——只读 diff 的审核是评论，不是验证。
- 审核者与被审者**不共享结论上下文**（不告诉它「作者觉得没问题」）。
- **风险加权，不平均分配**：数据破坏 > 公共接口 > 并发/状态 > 业务逻辑 > 格式样板。
- 建议换模型/provider 做审核，避免同模型共识性盲区。
- **必须能证伪测试本身**：① **非空转证明**——注入 `git show HEAD:<path>` 的**真旧实现**（最好签名兼容），确认新测试转红；② **反证用例**——每条告警/兜底类契约都要配一条**不触发**的用例，防「恒告警」也算过。

## 任务卡模板（贴进 team_task_create 的 description）

```
【背景】
【交付物】
【验收标准】命令 + 期望输出（写不出来就不许建卡）
【写 scope】文件/目录前缀（一人一域，重叠就拆任务）
【依赖】blocked_by 任务 id
【禁止事项】不许顺手动哪些文件/口径/公共接口
【审核级别】L1 自检 / L2 交叉 / L3 独立 / L4 对抗
```

## 回报格式（5 行内，硬性）

```
改了什么：
跑了什么命令：
原始输出：（关键行，不要贴全文）
阻塞：
下一步：
```

## 审核提示词模板

```
你的任务是【证明它不满足验收标准】，不是确认它满足。
输入：方案第 X 节 / 验收标准（逐条）/ 改动范围
要求：
1. 先写出你预计最可能出错的三处，再逐个去验证
2. 每条结论必须附【复现命令 + 原始输出】；没有原始输出的结论不要写
3. 不许说「看起来没问题」
输出：结论 PASS/FAIL；逐条验收（编号 → 结论 + 证据）；发现（[严重度] 文件:行 —— 描述 —— 证据）；未验证/不确定
```

## 失败升级阶梯

`补上下文重试 → 换人重做 → 主控收窄范围亲自做 → 降级交付并记录`

- 卡住的用 `interrupt_agent` 掐掉（保留 inbox），**不要用 `wait_agent` 干等**。
- 每阶段设时间盒 + 预算上限，超限就停下汇报，而不是继续烧。

## 主控自保（上下文是最真瓶颈）

- 只读三样：方案文档、任务卡回报、最终验收输出。**不读 diff**（diff 交给 verifier）。
- 任何「要读 10 个文件才能判断」的问题，派 subagent 读完给结论。
- **主控不当主力 writer**，否则会失去裁判身份。
- 只在 Gate 1 / Gate 2 / Gate 3 找人类；频繁被打断说明 `spec` / `plan` 没写清。

## 高频反模式

1. 计划只活在聊天里 → 审核无基准，必须落盘
2. 写域重叠还并行 → 先拆文件边界，再拆任务
3. 审核者 = 作者 → fresh context / 换模型
4. 任务没有可执行验收标准 → 不允许 complete
5. 多 agent 同跑迁移 / 格式化 / 代码生成 → 串行化，主控终局独占执行一次
6. 接口没冻结就并行 → 合并时两套假设
7. 均匀审核 → 浪费 80% 预算
